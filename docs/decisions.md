# Decisions

pitwall's settled decisions, each with its reasoning. A decision record here says what was decided and why, and often what was rejected and what's left for later, so you can learn why pitwall works the way it does without digging through pull requests.

- **Where they come from:** a decision starts in [`PLAN.md`](../PLAN.md) while it's open, with a lean. Once it's settled, its reasoning moves here, and `PLAN.md` keeps a one-line status. What's still open is in `PLAN.md`, under Decisions and Open questions.
- **IDs are stable:** D1 to D25 are cited across the repo, in the docs and in code comments. A decision that's revised, as D8 was after spike 003, keeps its ID and is updated in place.
- **How to read them:** M numbers are milestones and W numbers are work items, both in `PLAN.md`. A name and a date, such as "(Phil, 2026-10-23)", say who decided and when. Phil is Phil Leggetter, pitwall's author, and "I" and "me" are him too. "The coordinator" is the Claude Code session that coordinates the work.
- **By milestone:** D1 to D4 and D6 were settled from the first spikes, and D5, the stack, is Phil's choice. D6 took its current shape in M3 (W39, W42 and W59). D7 to D9 come from M2, D10 to D16 from M3, D17 to D20 from M3.1, D21 is the licence, D22, End session, came after M3.1 (W90), D23, a child's PATH, from M4's security review (W96, W98), D24, the config file, from M4's redesign (W103), and D25, cloning a PR's repo, from its actions (W107). Many have gained detail since.
- **Evidence:** the spike write-ups in [`spikes/`](spikes/), starting with [`001-session-control.md`](spikes/001-session-control.md).

## D1 - The session list comes from `claude agents --json --all`

- **Why:** it's a documented interface and returns in about 0.2 s with 20 sessions. It includes interactive sessions started in any terminal or IDE, not just background ones. Third-party session managers only see sessions they launch themselves, which is why pitwall exists.
- **Caveat:** interactive rows aren't in the agent view docs, which describe background sessions only. If they disappear in a later Claude Code release, pitwall loses most of its value, so watch the changelog.
- **How:** poll every 5 s by default (`pitwall --interval <seconds>`). The full snapshot is pushed only when it changed, with a heartbeat after other polls. Each `claude agents --json` call costs about 0.18 s of CPU, so a 2 s interval used about 9% of a core; that was the M1 behavior until W7a. Interactive rows give `status` (busy/idle) only; background rows add `state` and, when waiting, `waitingFor`.
- **`--all`, from M2:** background sessions that have finished or been stopped stay listed, muted, so they can still be opened, attached to (which restarts them) or removed. Plain `--json` drops them once their process has gone. It costs nothing measurable.
- **Ended interactive sessions,** which `--all` doesn't list once their process has gone, come from their transcripts instead, from M3.1 (D17).

## D2 - Interactive sessions: relay messages, or `/bg` for full control

- **Why:** an interactive session in Warp or Cursor belongs to that terminal. The only documented way in from outside is cross-session messaging. The receiving session sees such a message as coming from another session, "not typed by your user", so it can't approve a permission prompt or change configuration.
- **So:** pitwall relays messages through its relay, a headless session named `pitwall-relay` (D8): the page shows each send as "Message from pitwall", and the target sees a message from `pitwall-relay`. A relayed message still triggers real work: it starts a turn, and the session acts within its own permissions (spike 002). The relay arrives in M2, as a headless session pitwall runs, limited to `SendMessage` behind a gate (D8), which the M5 supervisor later takes over. For anything that needs full control, it asks me to run `/bg` in the session, then attaches.
- **Rejected:** posting to a session's inbox socket directly. Only the socket's auth line is documented, not the message format.
- **Waiting on you:** while an interactive session waits on you, its view says to answer in its terminal; a relayed message seems to wait until then (W47; not yet confirmed on a live dialog).
- **Ending one** (W90): pitwall can end an interactive session's Claude Code process, which leaves its terminal at the shell, and never closes the terminal itself (D22).

## D3 - Background sessions are driven through a PTY running `claude attach <id>`, shown with xterm.js

- **Why:** it gives the full Claude Code interface, including permission prompts and dialogs, without pitwall modeling any of it. `node-pty` works on Node 25. Closing the PTY detaches without stopping the session.
- **Dialogs in the conversation** (W49): an answered question dialog shows in the Conversation tab as its questions, options and your answers, read-only. pitwall still can't answer one, and an open one isn't in the transcript, so you answer it in the terminal.
- **In the view** (W47, W54): a running background session opens on its Terminal tab, which attaches, since that's the only place it takes input (Phil, 2026-10-22 and 2026-10-23). A finished one opens on Conversation, since attaching restarts it, and its footer says the Terminal tab asks first (D9). Preferences' "Open running background sessions on" can make running ones open on Conversation too; their footer then says to type to it in its Terminal tab, which attaches. There's no button for that, because opening the tab is what attaches (D9).
- **Rejected:** a custom chat UI over the transcript plus `claude --resume <id> --bg "prompt"`. It would look better but can't answer dialogs. The Conversation tab is that read-only view (W9).

## D4 - The supervisor is a background Claude Code session, not an Agent SDK app

- **Why:** a background session runs on the normal Claude login and shows up in agent view, and the web UI attaches to it like any other session (D3). Spike 002 showed it can do the job: it listed sessions, messaged a live interactive session without being blocked, got the reply back, and received that session's idle notice.
- **Limit:** a relayed request is only acted on if the receiving session's own instructions and permissions allow it. The supervisor can ask, not force.
- **Rejected for now:** the Agent SDK. Its structured message stream would make a better chat UI than a terminal. But it raises auth questions and parity questions, such as whether an SDK session binds an inbox socket (bare mode doesn't). Revisit if chatting with the supervisor through a terminal is too crude.
- **Reopened** (Phil, 2026-10-29): Phil chose a headless `claude -p` session with stream-json, as pitwall runs the relay (D8), shown in pitwall's own chat panel, over a background session in a terminal. He wants a workflow with its own UI rather than typing into a terminal, and pitwall needs to prompt the supervisor itself (M6), which a background session takes only through a PTY (spike 003). The relay has since settled the reasons above: a `-p` session runs on the normal login, binds an inbox socket and needs no trust step. The price: it isn't listed as a background session, and it stops with pitwall, which resumes it by session id. This decision is rewritten once spike 009 confirms that, and how approvals and pitwall's MCP server work there (PLAN.md, M5).

## D5 - Stack: TypeScript on Node >= 22, npm, Hono and `ws`, React and Vite, `node-pty`, xterm.js

- **Why:** TypeScript is the preferred language.
  - **Server:** Hono is small and runs on Node's HTTP server, and `ws` carries the PTY streams and live index updates.
  - **UI:** React and Vite, for a UI that's mostly lists and panels.
  - **Terminal:** `node-pty` and xterm.js are the usual pair for a terminal in the browser. VS Code's integrated terminal is built on both, and `node-pty@1.0.0` worked on Node 25.1.0 in spike 001.
- **Packaging:** the package is named `@leggetter/pitwall`, for npm, because the unscoped `pitwall` is taken. The binary is `pitwall`. It isn't published: `package.json` is marked private, so pitwall runs from a clone.
- **Watch:** `node-pty` is a native module. npm warned in spike 001 that its install script isn't covered by `allowScripts`, and npm 11 skips such scripts by default. On macOS that doesn't matter, since `node-pty` 1.1.0 loads the macOS build it ships with; on Linux it has none, so its script must run to compile it.

## D6 - Group sessions by repo, as the viewer chooses: by main repo, where they started, or every repo they worked in

- **Start group:** the repo of the session's working directory, by `git rev-parse --git-common-dir`, so worktrees sit under the repo they belong to. A directory below a root that isn't in a repo groups as itself.
- **The snapshot:** the server lists each session once, under the group it started in (Phil, 2026-10-21: "The problem is duplication"), and names the repos it worked in. The page groups it again for the viewer's Group sessions by, so switching is instant.
- **Group sessions by** (Phil, 2026-10-21, after a long session started in the root itself didn't show under the repo where it made 1,642 tool calls and 183 changes): kept as `pitwall.group-by.v1`, set in the Preferences dialog's Repo list section (W59; a header menu, View preferences, until then).
- **Preferences** (Phil, 2026-10-23: "I think the preferences pane should be a dialog with sections covering the area that's being configured"): a dialog from the header's button, 624 px wide, with a section per area: Repo list and Session view. Each change applies at once and the browser remembers it (W59). It doesn't repeat a setting that has a control of its own (W62; Phil, 2026-10-23: "I don't think we should duplicate settings that already have their own standalone buttons"): the single-key shortcuts are the shortcuts dialog's off switch, and the theme is the header's theme switch.
  - **Main repo, the default:** a session started in a root's own directory that worked in repos is listed under the one it changed most, ties broken by tool calls, the newest touch, then the path. It may be under another root, and so in that root's tab. A root-started session that worked in no repo stays under the root, and every other session stays where it started.
  - **Where it started:** the snapshot as it is.
  - **Every repo it worked in:** each session under where it started and every repo it worked in, except that the root's own group keeps only root-started sessions that worked in no repo.
- **Worked in:** the session view names every repo under a configured root that the session changed (an edit or write, a commit or push, a PR created or merged), or that at least 5% of its tool calls touched, sub-agents' included. The filter finds a session by any of them, so typing a repo's name in All sessions lists every session that started or worked there. Spike 004 scored that rule at 1 false positive and 3 misses on 28 hand-judged repos.
- **Why not list it under each repo it worked in:** M3 did that at first (W34), because most sessions start in the folder that holds the repos. In the try-out, 12 of 20 sessions were in more than one group, and Phil found the duplication worse than a large root group ("The problem is duplication").
- **How:** a background scanner reads each session's transcripts, sub-agents' included, and the poll never waits on it. It keeps what it finds in memory only, and runs read-only git at repo boundaries, at most two processes at once. A scan never moves a session. Reading a tool call is linear in its size, and a word over 4,096 characters or a command over 256 KiB names nothing, so one crafted call can't stall the server (W50).
- **Counts:** in Main repo and Where it started, each session is in one group, so the groups' counts under a root add up to that root's sessions. In Every repo it worked in, a repo's count is its distinct sessions, so the counts can add up to more than All sessions. Needs you, All sessions and the root tabs' badges count each session once in every mode.
- **Hiding** (Phil, 2026-10-21): a repo or directory can be hidden from the repo list, and the hidden ones are listed at its foot, to select or unhide. It changes only the repo list: its sessions still show in Needs you and All sessions. Chosen over ageing old repos out, after the try-out found a long session still listed under a repo it last worked in 44 days before its latest work.

## D7 - The browser is opened through a launch file, not a URL with the token in it

- **Why:** macOS lets any user read every process's arguments with `ps`, so `open http://127.0.0.1:<port>/#token=...` exposes the token to other accounts on the machine. Instead, the CLI writes a small HTML page that sends the browser on to the token URL. The page sits in a file only you can read (0600, in a 0700 `~/.pitwall/` directory), and the CLI opens that file, so `ps` shows only a path. The file is deleted once the page has used it, after 60 s, or on exit, whichever comes first; with a fixed token, only after 60 s or on exit (W51). Jupyter uses a launch file the same way.
- **Rejected:** a single-use launch code in the URL. It's still visible in `ps` briefly, and another user who used it first would get the token while your browser failed.
- **A fixed token, opt-in** (Phil, 2026-10-21): each run mints its own token unless `PITWALL_TOKEN` is set; empty counts as unset. The CLI reads it from its environment only, never from a `.env`, since a repo it runs in could otherwise pick the token. `npm run dev` also reads it from the pitwall repo's own `.env`, found from the script's location, never the current directory (`.env.example` shows how to make one). Both say at start that the token is fixed, and neither ever prints it (W51, after W48 found the CLI printing it at every start): the CLI prints `http://127.0.0.1:<port>/` and says the token is `PITWALL_TOKEN`'s, on every start and dev restart, and `npm run dev` marks its own per-run token with `PITWALL_TOKEN_PER_RUN=1`, which it never takes from the environment or the `.env`; the CLI honours it only with `PITWALL_OPEN_MARKER` set too, as `npm run dev` sets both, so set by hand without the marker it's ignored and the token is fixed (W58). The rule: a token that outlives the run is written nowhere but the launch file. With a fixed token, that file isn't deleted at the first authentication, only after 60 s or on exit, because a pinned tab reconnects before a new tab reads it; the token is in the environment or a 0600 `.env` for the run's life anyway. `npm run dev` reads the `.env` only when it's yours and not readable by others, and a token with fewer than 8 different characters, or one piece repeated, is refused. A tab that holds the token then reconnects by itself when pitwall restarts on the same port, which keeps a pinned tab working. A new tab needs `#token=` and the token added to the address. But any page or script that ever saw the token can drive every later run that uses it, so use it only on a single-user machine or for development. A fallback port changes every run, so the CLI says to use `--port` for a pinned tab.
- **Residual with a fixed token** (W48): the launch redirect puts `http://127.0.0.1:<port>/#token=<token>` in the browser's history (History, Top Sites, Sessions, and synced if history sync is on), although the page clears the address bar. Chrome also writes the tab's `sessionStorage`, token included, to the profile on disk. Both belong to the same user and are harmless for a per-run token once its run ends; a fixed token found there stays valid. Later: a single-use launch code in the fragment, traded over the WebSocket, would keep any token out of history. The launch code rejected above was rejected only because of `ps`, which the launch file has since removed.
- **Rejected for pinned tabs:** a hand-off of each run's token to the pitwall tabs already open, with `pitwall open` for browser restarts, built and removed before merge (Phil, 2026-10-21), because a page another account's process served on the port, still open when pitwall started, would have received the token; the token in `localStorage` (D14); and a cookie, which browsers share across ports on 127.0.0.1.
- **Context:** W6 review finding 1. It's part of the M2 security gate, together with challenge-response WebSocket auth and dev readiness, because from M2 on the token authorizes typing into agents.

## D8 - Messages to interactive sessions go through one headless relay session

- **Why:** only a Claude session can call `SendMessage`, and the socket's message format isn't documented (D2). Pitwall runs one headless session as its own child process, `claude -p` with stream-json input and output, named `pitwall-relay`, on Haiku, with `SendMessage` as its only tool. It passes your text on verbatim, except that spaces that look like a space (U+00A0, U+2000 to U+200A, U+202F and U+205F) become a plain space and CRLF becomes LF (W43): the relay's model tends to write those as plain ones, and the gate, which compares exactly, then blocked the copy. It starts on first use, takes each message on stdin, so the text never appears in `ps`, and stops with pitwall.
- **The gate:** a `PreToolUse` hook allows each `SendMessage` only when it's the exact message you asked for, to the session you picked, once, and fails closed. The relay loads none of your settings, hooks, plugins or `CLAUDE.md`. Added after the M2 security review found that any local session could talk the relay into sending; anything it tries that you didn't ask for shows as an alert in the UI, except a copy of your message whose text alone changed, which pitwall tries again (below). Needs Claude Code 2.1.295 or later, which pitwall checks before it starts the relay. A denial exits with code 2, so nothing else printed alongside it can turn it into an allow, and the relay runs without code-loading variables such as `NODE_OPTIONS`.
- **A changed copy:** when the gate blocks the relay's copy of your own message and only its text differs, pitwall tries once more on a new relay, with no alert (W43, W52). That's safe because Claude Code's own tool result says the call never ran, and the new relay is outside whatever may have primed the old one. The relay's model drops or changes text in long copies (W52's live check saw 447 characters dropped from a 6,000-character message, and the second copy arrived exactly), so an alert there would be routine. The message's result says so instead: when the second copy goes through, that the first was blocked and where it differed; when it's blocked too, that nothing was sent and where each copy first differed, by line and character code, never with the text. A copy that differs in more than its text, such as another recipient, idle notices or a field pitwall doesn't check, isn't tried again and raises an alert, since a peer may have talked the relay into it (W48's F3), and so does the relay trying your message again in the same turn. The alert says whether it was a message nobody asked for, a changed copy of yours or a repeat of yours. No alert is raised for your own message that ran without the gate checking it; that turns messaging off, with the reason in the app strip.
- **Not a background session:** that was the first decision, on 2026-10-16. Spike 003 found that a running background session can't take a new prompt without a terminal. Driving it through a PTY works, but it scrapes a screen meant for people, puts your text in `ps`, and needs a one-time trust step.
- **Duplicate names:** `ListAgents` doesn't show directories, so when two running sessions share a name, nothing is sent and pitwall asks you to `/rename` one.
- **Replies** (W46, Phil, 2026-10-22): a session's `SendMessage` to the relay, usually its reply, shows in that session's conversation as "To pitwall-relay", in full and as markdown, in place of the tool call. It's read from the session's own transcript: a call counts when it's to the relay's name, or to a socket that a message from the relay's name came from earlier in that transcript; pitwall keeps the newest 64 such sockets per session, in memory. The label claims only the name addressed, since any local session can take the relay's name (W48). Once the conversation shows at least as much as the relay's own 2 KiB copy (`RelayExchange.reply`), the message box keeps only its status line, which says so; until then the copy stays there. Because it's read from the transcript, a reply is still shown after pitwall restarts.
- **Trade-off:** a reply that arrives after pitwall exits isn't shown in pitwall. The target's own conversation still has it.
- **Later:** the M5 supervisor replaces it.

## D9 - At most four attached sessions, and a confirmation before restarting one

- **Why:** each attach is a PTY and a `claude attach` process. Closing the view or the tab detaches, and the session keeps running. `claude attach` restarts a background session that isn't running, which is an action, so the UI asks first.
- **Opening a view attaches** (W54): a running background session's view opens on its Terminal tab, so opening one takes one of the four. In a root tab only the open view's terminal is attached; views kept for other root tabs keep theirs (D16). A fifth gets "4 sessions are already attached; detach one first.", with Attach again, as before. Stepping with `j`, `k`, ↑ or ↓ waits 500 ms before attaching, so passing through takes none. The terminal takes the keyboard only right after you opened the view or its Terminal tab with a click or Enter in the page, within 5 s, and while focus is still in the view (W57, after W48's second pass found H1). A URL, a reload, back or forward, a root tab's switch or a step attaches but leaves focus where it is, and the terminal's bar says "Click the terminal, or Tab to it, to type to the session", so the next Enter after a reload can't approve a permission prompt. `pitwall.terminal-focus.v1` can make it never (Phil, 2026-10-23); its control is "The terminal takes the keyboard", in Preferences' Session view section (W59).

## D10 - pitwall's own design system, inspired by Hookdeck's UX

- **What:** [`docs/design-system.md`](design-system.md) is the spec: tokens by role (surface, text, border, tone) for light and dark, type, spacing, components, states, layout and keyboard. A dev-only gallery in the app (`#uikit`) shows each component, and the production build leaves it out. It's pitwall's own design system, not Hookdeck's, and it uses no Hookdeck logos or artwork.
- **Contrast:** every text color pair meets WCAG AA in both themes, and `contrast.test.tsx` checks them. Disabled text is the one exemption, as WCAG 1.4.3 allows for inactive controls.
- **Fonts and icons:** Inter and JetBrains Mono (both OFL 1.1), self-hosted, because the CSP (`default-src 'self'`) blocks Google Fonts. Icons are Material Symbols Rounded (Apache 2.0), bundled as SVGs behind a name map that `scripts/extract-icons.ts` generates. The theme's pre-paint script is a same-origin file for the same reason. The licenses are in [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md).

## D11 - Three columns: repos, then sessions, then the open session

- **Why:** asked for after trying M2: pick a repo, then one of its sessions, then work with that session. It replaces M2's single list of grouped cards.
- **Repo list:** Needs you, All sessions and Starred first (Starred shows whether or not anything is starred, so the list never jumps; W53), then the root's own directory, labelled with its path, then the repos in alphanumeric order, so the list never jumps.
- **A started session is selected** (Phil, 2026-10-23: "when creating a new session, it should be automatically selected - the repo/directory and the session"): once a session started from New session is listed, its root tab, its repo or directory under Group sessions by, and its view are selected, in one history entry, and its terminal takes no keyboard focus (W57). When that would take over a draft, a running Stop or Remove, an open confirmation or restart prompt, or typing, a toast says it's listed, with Open, for 10 s; its row is the lasting way in (W63).
- **Widths:** three columns from 1,200 px. Below that, the session view lies over the session list, starting below the header, and what it covers is inert (it can't be clicked or tabbed to). Below 900 px the repo list is a drawer, and at 600 px and narrower the session view is full width, with Back to sessions.
- **Resizing:** the session view is 760 px by default and at least 560 px, about 80 terminal columns. The divider resizes it, and so do the actions menu's Make view wider and Make view narrower, for anyone who can't drag (WCAG 2.5.7). The width is remembered.

## D12 - Two-line rows without a needs-you tint, sorted by urgency

- **Rows:** name, title, badge and time, then what the session asked or was last asked. The last reply, the relay exchange, the working directory, the attach command and the message box are in the session view.
- **No tint:** rows that need you keep their bar and badge, without a yellow background. Nine of fifteen sessions needed attention on 2026-10-20, and the tint turned most of the list yellow.
- **No idle badge in the list:** "Idle" shows only in the session view. Needs you is still inferred, never from the badge: `needsAttention()` is true when the index has set the session's `needsYou`, judged from its context since W69 (D18), and never for a stale, finished or ended session, nor for one the viewer marked Not needed now, until what it needs changes (W88).
- **Sort:** Urgency by default, or Recent or Name. The order holds while the pointer or focus is in the list, so rows don't move under you.

## D13 - ⌘↵ sends, and the single-key shortcuts can be turned off

- **Sending:** ⌘↵ (Ctrl+Enter on other platforms) sends, and Enter adds a line. Each message starts a turn on the target session's model and can't be taken back, so a stray Enter mustn't send.
- **When a send's outcome is unknown:** no answer, a server error or a success pitwall can't read. The UI says the message may have reached the session and to check its conversation, rather than inviting a resend that would start another turn.
- **Shortcuts:** `/`, `n`, `?`, `j`/`k` and `s` (star the open session, W53). They're ignored while you type, in the terminal, with ⌘, Ctrl or Alt held, and while an input method composes. A setting in the shortcuts dialog turns them off (WCAG 2.1.4), and the browser remembers it; Preferences doesn't repeat it (W62). Onto a running background session, `j` and `k` attach only once it has stayed open for half a second, and its terminal then takes no focus, so the next `j` or `k` still steps (W54). Nor does it take focus after a reload, the URL or the back button: with nothing focused, `j` and `k` are still the shortcuts, never keys for the session (W57).
- **Leaving the terminal:** F6 moves focus from the attached terminal to its tab, so the terminal isn't a keyboard trap (WCAG 2.1.2). Claude Code's docs bind nothing to F6 (checked 2026-10-21).
- **A new line in the terminal** (Phil, 2026-10-21): Shift+Enter sends a line feed (Ctrl+J), which Claude Code's docs give as a new line in every terminal with no setup. xterm.js would send Enter's carriage return, which submits. Not with Ctrl, Alt or ⌘ as well, nor while an input method composes.

## D14 - The live snapshot carries only what the list shows

- **Why:** until M3, every snapshot sent to the browser held each session's latest reply, though the UI showed none of it. That's gone.
- **What it still carries:** what the list and the session view's header show: each session's title, its newest prompt (up to 300 characters, one typed while Claude worked included, W99), what it asked you, a background job's own line on what it needs (up to 200 characters, D18), how many of its sub-agents are running, the reply to a message you relayed, and its `prLinks` (M4, W94). Those are links to the pull requests it opened, pushed to, was linked to by Claude Code's own `pr-link` entries (W105) or was given in a prompt, up to 200 of them (`PR_LINKS_STRONG_MAX`), and up to 20 of the ones Claude named (`PR_LINKS_MAX`), each a lowercase `owner/name`, a number or the branch pushed, and when. Until W105 one cap of 20 held them all, and 10 of Phil's sessions lost older strong links. The index doesn't know which PRs are open or whose they are, and keeps every link. **The server sends each session only the links that match a PR in the current PR list** (`prLinkMatches()`, `src/server/snapshotLinks.ts`, W105's review), on `GET /api/snapshot` and the WebSocket alike, and sends the snapshot again when a new list changes what it carries, so the page's owners, Finished and "Mentioned in" lose nothing. Before the first fetch and with `--no-prs`, no link is sent: the page shows only those that match one of your open PRs (W96, W98).
  - **Why** (W105, measured on Phil's machine on 2026-10-29, counts and bytes only): with 60 sessions listed, 43 with links, uncapped strong links took the links from 389 to 1,056 (324 'linked', 306 'opened', 261 'mentioned', 122 'pushed', 43 'prompted'), from 39,301 to 104,743 bytes of JSON, and the whole snapshot from 85,367 to 150,809 bytes, sent again after nearly every 5 s poll while a session works. Most were links to PRs that aren't open. Cut to his 61 open PRs, 94 links in 17 sessions are sent, 9,424 bytes, and the snapshot is 55,204 bytes; with no links at all, 45,593. The conversation itself leaves the server only when you open it, through the token-gated conversation route, and a sub-agent's list and transcript only through their own (W76).
- **Browser storage:** no token in `localStorage`, and no session content, with one exception. The token is in `sessionStorage`. So is each conversation's unsent draft, under `pitwall.draft.v1:<sessionId>`, with whether a send of it was out or uncertain, and when (W44). Phil chose `sessionStorage` over `localStorage` (2026-10-22): a draft lasts as long as the tab, as the token does, through reloads and pitwall restarts, and two tabs never overwrite each other's. The browser keeps `sessionStorage` in its profile on disk while the tab exists, and for a closed tab it can reopen (W48's F10). A process that takes pitwall's port while pitwall is down serves the tab's next reload on pitwall's origin, and can read the token and the drafts: D7's single-user caveat covers it (W48). Browsers do copy a tab's `sessionStorage` into a duplicated tab, and bring it back with a reopened one. The draft's text goes nowhere else. `localStorage` holds UI state under `pitwall.*.v1` keys: preferences, plus the filesystem paths of roots and repos in `pitwall.view.v1`, `pitwall.finished.v1`, `pitwall.root-tab.v1` and `pitwall.hidden.v1:<root>`. - **Browser history:** what's selected and what's open are in the page's URL, so the browser's history keeps them, as it keeps any address: `?repo=` holds a repo's path (W21), `?root=` a root's path, for its tab (D16), `?session=` a session's id, and, since M4, `?pr=<owner>/<name>/<number>` a pull request's repo name and number (W95). ## D17 - Ended interactive sessions are listed from their transcripts, and resumed in the background

- **Why:** an interactive session belongs to its terminal's process. Once that's gone, as when the terminal closes or the machine restarts, Claude Code drops it from `claude agents --all`, though its transcript stays (Phil, 2026-10-23, after a laptop restart: "Why aren't some sessions being picked up so I can restart them in pitwall?"). Spike 006 found that `claude --resume <id> --bg`, with no prompt, brings one back as a background session under its own id, name and model, which pitwall can attach to (D3).
- **What's listed** (Phil, 2026-10-27): sessions that ended in the last 7 days, with Show older for up to 30, at most 100. They sit in their group's Finished section, muted and labelled Ended, and never in Needs you. An unnamed one is named by its directory and the start of its id, since Claude Code's default name isn't recorded.
- **Which transcripts count:** a session started in a terminal (not `claude -p`, so never pitwall's relay), with a prompt you typed, and a UUID session id that no `claude agents --all` row has. Not one that last ran in the background, since `claude rm` leaves its transcript, nor one whose conversation went on under another id, as after `/bg`.
- **The view** offers Resume in background, after which it opens on the Terminal tab, as any running background session does (D9), and Copy command, `cd <dir> && claude --resume <id>`, to carry on in a terminal.
- **Safety:** the server checks a fresh `claude agents --json --all` first, since a session still open in a terminal would get a copy, then the directory, and runs in the real path it just checked, under spawn's limit of 5 starts a minute (W73's security look, fixed in W81). If a copy starts anyway, it says so with Claude Code's note.
- **Background sessions that have stopped too** (W107): an ended session that owns an open PR stays in the main list until the PR closes (W106), so its row offers Resume as well as its view, and so does a stopped or finished background job's, which W106 keeps listed the same way. `claude --resume <id> --bg` wakes such a job in place, under its own short id, with its saved name and model ("note: woke session <id> with its saved options", checked live on Claude Code 2.1.312 with a throwaway job), so the same route takes it, after a fresh `claude agents` that lists its row with no process; one whose row has a process, an interactive row, or none at all is refused.
- **No command to copy for a path with `'` or `\`** (W85's security review, fixed in W87): inside single quotes zsh and bash take every character as it is, but fish reads `\'` as a quote. POSIX's `'\''` for a `'` would end fish's word early, so a directory named to hold a command would run it when the copy was pasted into fish. Without those two characters, single quotes are one word in all of them. So Copy command, and spawn and resume's trust command, aren't offered for such a path, and the page says why. The finding is from fish's documented quoting, not a run in fish.

## D18 - Needs you is judged from each session's context

- **Why** (Phil, 2026-10-27: "the context of the session should really determine if anything is needed of the user"): a session pitwall resumed came back `blocked` with Claude Code's "send a prompt to start", and counted in Needs you though it had asked nothing. Spike 007 found what Claude Code records: a background job's own `needs` line, which a stop clears and a restart doesn't bring back, while the transcript keeps the question and marks each turn's end.
- **The rule:** a session needs you for one of five reasons, checked on every snapshot, pitwall's first included, so Needs you after a restart is this assessment, not Claude Code's bare state.
  1. A prompt on screen.
  2. A background job's `needs` line, shown as the reason, unless it's the start placeholder. It's read from `~/.claude/jobs/<id>/state.json`, an internal file, behind one adapter that fails soft.
  3. Its last turn asked you something, with the turn's end read from the transcript, since a plugin's monitor keeps Claude Code's status at busy.
  4. You resumed it, or confirmed a restart, in this run of pitwall, and it's had no prompt since. Phil confirmed this reading of his words; the other, that waiting for a prompt never counts, was ruled out.
  5. `blocked` with a job file pitwall couldn't read, so a question is never hidden.
- **The index decides,** not the web UI, so the count, the list and the sort agree. Reason 4 is kept in memory, so it ends when pitwall restarts. A blocked session that doesn't need you loses the solid Blocked badge, since solid is for needs you only.
- **Not now:** Claude Code's recap (`away_summary`) and a model's judgement. Both are M6's refinement of reason 3, with the supervisor.
- **Through a pull request** (M4 redesign, W106; Phil, 2026-10-29: "A row needs you when its session does, or its PR does: failing checks, conflicts, changes requested or a review request"): a row is a piece of work, a session, an open PR or both. So a session's row also needs you while an open PR it owns needs attention (`prNeedsAttention()`: your own with failing checks, conflicts or changes requested, or one that asks your review, of you or a team you're on), whatever the session's own state, ended included, and a PR row no session owns needs you while its PR does. A mention never counts, nor another author's failing checks or conflicts, which are theirs to fix. Line 2 gives the reason: "CI is failing on #128", "#128 has merge conflicts", "Changes are requested on #128" or "Your review is requested on #128" on a session's row, unless the session needs you itself, and "CI is failing" and the like on a PR row.
  - **The page decides this part,** from the index's `needsYou` and the PR list, since the index never waits on GitHub (W94). Every count, Needs you, the repo list's badges, the root tabs' and the page title, and the Urgency sort, count a row that needs you through a PR. Until W106 PRs never counted in Needs you, and their counts were subtle danger.
  - **Not needed now** (W88) is for what the session needs: a session marked so that still needs you through a PR stays in Needs you, line 2 saying why, and a row that needs you only through a PR has no toggle. Snoozing a PR's state could be a follow-up.

## D22 - End session sends a running interactive session's process SIGTERM, and only an idle one without a stronger warning

- **Why** (Phil, 2026-10-21: "close a session and kill the terminal process", worried about side effects; approved 2026-10-28 as W90): an interactive session belongs to its terminal (D2), and Claude Code documents no way to end one from outside it. Spike 005 found that signalling its Claude Code process ends it in about a second: its SessionEnd hooks run, its MCP servers, background commands and sub-agents end with it, nothing is orphaned, its transcript stays whole, and `claude --resume` brings it back. pitwall never closes the terminal tab: its parent process isn't always a shell, and ending that would end everything else in the tab.
- **The signal: SIGTERM, once.** All three that spike 005 tried end a session in 0.6 to 1.8 s, but they differ:
  - **SIGTERM** exits 143, which a shell can tell from a normal `/exit`, and git cleans up its lock files on it.
  - **SIGINT** exits 0, which looks like `/exit`.
  - **SIGHUP** exits 129 and says the terminal hung up, when it hasn't.
  - **Never SIGKILL,** and nothing after the SIGTERM: SIGKILL skips the hooks and git's clean-up, and the spike recommends no escalation.
  - **The wait:** the server waits up to 5 s for the process to exit, by the clock, and says whether it did. Each `ps` after the signal gets only the time left and is abandoned when it runs out, so a `ps` that hangs can't hold the request, its command slot or the session's lock past the wait (W90's review).
- **What it costs,** which the confirmation says:
  - a reply being written is lost, since Claude Code writes a reply to the transcript only once it's finished;
  - running commands, background commands and sub-agents are killed, not moved to the background as `/exit`'s dialog offers;
  - a commit in progress doesn't happen, though spike 005 found the repo left consistent, with no lock.
- **The guards,** all on the server; if any one refuses, nothing is signalled:
  - **Who asks:** the apiKey, this server's Origin and an exact Host, as for every state-changing route.
  - **Which session:** one the snapshot lists as a running interactive session, with a pid and a UUID id.
  - **A fresh listing:** `claude agents --json --all` lists it as interactive, with the snapshot's pid. Every row it printed counts, including rows pitwall's parser skips for an unknown kind, a relative directory or no start, and a second row for the same session. No other row may name that pid, and no row may name another pid for the session (W90's review).
  - **Not a relay:** not this pitwall's own relay, and not any session named `pitwall-relay`, in the snapshot or the listing, as another pitwall's relay would be (W90's review).
  - **The same process:** `ps` says the pid is `claude`. Its start time and command are read before that listing and again just before the signal, and must match exactly, so a pid reused meanwhile can't be hit.
  - **Not a reused pid:** the process started no later than the session's `startedAt` from the listing, with no slack. That holds for the session's own process every time: `ps`'s `lstart` is whole seconds, rounded down, so it's never later than the real start, and Claude Code writes `startedAt` after its process has started. W90's live checks saw `startedAt` 0.5 to 1.7 s after `lstart`. That includes a session resumed with `claude --resume <id>`, whose `startedAt` is its new process's, not the original session's. A process that started later is one that took a dead session's pid. The 2 s of slack W90 first allowed went in its review, which asked for it to be needed or gone: it let through a pid taken up to 2 s after the session started, and nothing needed it. A wall-clock step forward after the process started could make it refuse a session's own process, on Linux, where `ps` works `lstart` out from the boot time. That fails safe, with a 409.
  - **Never pitwall:** not pitwall's own process, nor one pitwall runs under (Phil's dev pitwall once ran under the coordinator's session), nor one it started, as its relay is. It checks `ps`'s parent pids.
  - **Idle only,** unless you confirm a stronger warning. Its turn must have ended by its transcript, read afresh by W69's rule, with no prompt on screen. None of its sub-agents may be running, by a scan that starts then. "Idle" can't come from Claude Code's status, which a plugin's monitor keeps at busy (spike 005, finding 8). A working session gets a 409 naming what runs, the page shows the stronger warning, and only its End session anyway sends `whileWorking`. A transcript that can't say, or sub-agents that can't be read, count as working: a scan that fails, or can't read the session's transcript or its `subagents` folder, says `unknown`, not 0 (W90's review).
  - **Limits:** at most 5 ends a minute, as well as the 4 commands at once it shares with stop, remove, resume and open.
- **Asks first,** as Stop and Remove do: an inline confirmation naming the session and its running sub-agents, and what ending costs. The name is in its own `<bdi>`, so a right-to-left name, or the directional marks W87 keeps in names, can't reorder the sentence around it. Afterwards the session leaves `claude agents` at once (spike 005, finding 5), so the next snapshot lists it as ended, with Resume in background and Copy command (D17).
- **`ps` isn't Claude Code's interface,** but its fields here are POSIX's. pitwall reads only a pid's start time and command name, and the table of parent pids, never a command line, which can carry another process's secrets: spike 005's process listings showed an API key in an MCP server's URL. It fails soft: when `ps` can't say, nothing is signalled.
- **Not now:**
  - a session whose process isn't named `claude`, as when Claude Code runs through Node, which End session refuses;
  - naming running background commands in the warning, which the transcript doesn't record reliably;
  - a live check of a session switched to with `/resume` inside a running Claude Code, rather than `claude --resume` in a new process. If its `startedAt` were the original session's, which is earlier than the process's start, End would refuse it, failing safe with a 409. No live check has driven `/resume`'s picker, which is a dialog the live checks' driver never types into.

## D23 - A child's PATH keeps only its absolute directories

- **Why** (W96's finding, W98): Node's spawn and node-pty's `execvp` search PATH as a shell does, so an empty entry (`a::b`, or a leading or trailing `:`), a relative one (`.`, `bin`, `./node_modules/.bin`) or an empty PATH makes a bare `claude`, `gh`, `git`, `ps` or `open` resolve in the child's working directory. pitwall runs stop and remove in the temp directory, and ran gh there until W107's clone and W117's searches moved it into a 0700 directory of its own, and on Linux `/tmp` is shared: another local user could plant `/tmp/gh` there, and pitwall would run it as you.
- **What every child gets** (`childEnvironment()` in `src/index/exec.ts`): PATH's absolute entries, in their order. An entry that is `~` or starts with `~/` is your home directory and the rest, in its place, as bash reads `~` and `~/` in its own command search, from the child's own `HOME` when that's absolute, else `os.homedir()`. That keeps a literal `~/.dotnet/tools`, which the .NET SDK's `/etc/paths.d/dotnet-cli-tools` puts on a Mac's PATH, working (coordinator, 2026-10-29). `~user/...`, and a `~` entry whose home directory has a `:` in it, are dropped with the other relative entries. When no entry is left, PATH is `/usr/bin:/bin`, libuv's own default, rather than empty, which searches the working directory too, or absent, which leaves a bash further down its own default, which ends in `.`. Editor detection searches the same PATH (`src/server/editors.ts`).
- **POSIX only:** Windows' own lookup searches the working directory first, whatever PATH says, and pitwall hasn't been run on Windows, so there PATH passes through unchanged.
- **What it costs, accepted** (coordinator, 2026-10-29): sessions pitwall starts or resumes lose project-relative PATH entries, such as `./node_modules/.bin`, `bin` or `.`, which a session started in a terminal keeps. Phil's PATH has no relative entry but `~/.dotnet/tools`, which is expanded.
- **The other way, if anyone needs those entries:** resolve `claude` to an absolute path from the filtered PATH, and pass the user's own PATH through unchanged for spawn and resume only, the two that run in a directory the user chose rather than the temp directory.
- **Not covered:** `scripts/dev.ts`, dev tooling run in pitwall's own checkout, starts `tsx` with the environment it was given, unfiltered.

## D24 - A config file beside the flags

- **Why** (Phil, 2026-10-29: "a minimal one now, with roots and their GitHub owners"; [#101](https://github.com/leggetter/pitwall/issues/101)): the M4 redesign lists a pull request under the root whose GitHub owners cover it, and that's a per-root setting no flag holds well. The roots themselves are retyped on every run. So pitwall gets a config file now, with only those two settings (W103); the rest of #101 (the port, the interval, the PR searches, M5's supervisor and recaps) can join it later.
- **Where:** `config.json` in pitwall's folder, `~/.pitwall` or `PITWALL_HOME`, beside its other files, so `PITWALL_HOME` moves it too; or the file `--config <path>` names, resolved against the current directory, a leading `~` expanded. A missing default file means every setting is its default; a missing `--config` file is an error, since you asked for it. Rejected for now: `~/.config/pitwall/` (XDG), which would split pitwall's files across two folders.
- **Format:** JSON with comments, `//` and `/* */`, and trailing commas, which `stripJsonComments()` in `src/config.ts` replaces with spaces outside strings, so an offset in what JSON.parse reads is the same in the file as written. A few lines of code instead of a dependency (AGENTS.md); TOML or YAML would need one.
- **Shape:** `{ "roots": [ "~/oss", { "path": "~/work", "github": { "owners": ["example-co"] } } ] }`. A root is a path, absolute, `~` alone or starting with `~/`, or an object with `path` and `github`. A relative path is an error, since relative to what isn't clear in a file, and so is `~user`. `github.owners` is a list of owners, `"all"`, for every owner no other root lists, or `"none"`, for the root's own clones only. Owners must match `GITHUB_OWNER_PATTERN`, and are lowercased and deduped. One starting like a GitHub token (`gh` and one of `pousr`, then `_`, or `github_pat_`) is refused: no user or org name has a `_`, and the pattern alone would let a pasted token through, into the UI once RootOwners carries it. An owner on two roots, two roots with `"all"`, the same directory twice by real path, and an empty list are errors: each leaves it unclear which root a PR belongs to. A root without `github.owners` gets its owners from its clones (PLAN.md, "Settled").
- **Precedence:** a flag, then an environment variable, then the file, then the default. Roots given as arguments replace the file's, not add to them, as #101 proposed. A root given as an argument still gets its `github` settings when its real path equals a configured root's, so `pitwall ~/work` alone keeps `~/work`'s owners. The PR side gets them as `ownersByRoot()`'s map, keyed by real path as the index's roots are; a root absent from it infers its owners from its clones. Real paths come from `realpathSync.native`, which, as the index's `fs.promises.realpath`, gives the case on disk: on a case-insensitive file system such as APFS, JavaScript's `realpathSync` keeps the case as typed, so `~/Work` for `~/work` would miss the index's root, lose its owners, and not be caught as a duplicate of `~/work` (W103's review).
- **Validation:** a bad value stops pitwall before anything starts, with a message naming the key, such as `"roots[1].github.owners"`, and the file, as a bad flag does. No message quotes a value from the file, which could be a pasted secret: a value of the wrong type is described by its type, a bad path or owner by what it must be, and invalid JSON by its line and column, from `jsonErrorAt()`, never V8's own message, which quotes the text around the error. Keys are JSON-quoted, so control characters are escaped, and cut short; so is a duplicate root's real path, in full. Parsing is linear: a megabyte of roots or owners takes about 0.1 s. An unknown key, at any level, is a warning on stderr, and the rest is read, so an older pitwall can read a newer file.
- **Security:**
  - **No token:** a key named like one, anywhere in the file (`token`, or ending in it, ignoring case, `-`, `_` and `.`, such as `PITWALL_TOKEN` or `githubToken`), is an error saying PITWALL_TOKEN comes from the environment only, and never quotes the value. So is a GitHub token anywhere, as a key or in a string: one of GitHub's prefixes and at least 20 more characters; the message names where it is, never the token. A token in a file lasts longer and travels further, into backups and dotfiles repos, than one in the environment. `maxTokens`, say, isn't caught.
  - **Its owner and mode, on POSIX:** the file decides which directories pitwall reads and which sessions it lists, so pitwall refuses one that isn't the current user's or that group or others can write to. Others may read it: it holds no secret. It's checked with fstat on the opened file, never stat then open, so what's checked is what's read, as npm run dev reads its `.env` (W51). It's opened with O_NONBLOCK, so a FIFO is refused rather than waited on, and anything that isn't a regular file is refused. A symbolic link is followed, as a dotfiles repo may have it, and the file it points to is what's checked. Over 1 MiB is refused, by its size and again while reading, which stops at 1 MiB and a byte: a file can grow after fstat, and some, such as Linux's `/proc` files, say they're empty. Windows has no POSIX owner or mode bits, so there only the file check applies.
  - **It can't weaken the security rules** (PLAN.md's Security section): no setting binds beyond 127.0.0.1, turns off the token, or skips the `Host` or `Origin` checks, and none may be added.
  - **No per-repo config files:** a file inside a repo could change what pitwall does from code you haven't reviewed. pitwall reads only the one file.
- **Not now:** the rest of #101's settings; `pitwall config`, printing each setting and where it came from (pitwall prints the file it used at start); reloading on change, since it's read at start only; and browser preferences, which stay per browser (D14).

## D25 - Cloning a pull request's repo is the server's decision, after a click

- **Why** (Phil, 2026-10-29: "Starting a session for it creates the directory, by cloning it into the root, after a click that shows the path"; W107): a PR whose repo has no clone under the roots (`PullRequestPlace` 'not-cloned', W105) can't have a session until there's a directory to start it in. Cloning writes into one of your roots and reaches GitHub, so it's one more thing a page that can reach pitwall could make it do. The rules keep that to exactly what you clicked for.
- **The page names only the repo** (`CloneRequest`, `CLONE_PATH`). The server clones it only when a PR in its own current list, from gh's searches of your PRs, those asking your review and those mentioning you, is in that repo and placed 'not-cloned'; it takes the root from that place, never the request, and only while the snapshot lists it as a root at its own real path; and the directory's name from GitHub's spelling of the repo's name, refused when it's `.`, `..` or starts with `.`, or isn't one GitHub allows (`GITHUB_REPO_NAME_PATTERN`). So a page can't clone an arbitrary repo, or into an arbitrary place.
- **Never into your home folder, or a folder above it** (W108's finding, W117): the config file allows a root at `~`, and a clone there could make `~/bin`, which Ubuntu's default `~/.profile` puts on PATH once it exists, or `~/Applications`, where `src/server/editors.ts` looks for editors' bundles. So a root that is your home folder, or holds it, by real path, is refused with 409 and a message saying why; and when pitwall can't find your home folder, every clone is, since it can't tell. Give a folder inside your home folder the owner in the config file instead.
- **Which owners a root claims, for a clone** (W108's finding, W117; the coordinator's call, safer and reversible while Phil was offline): anyone can open a PR on their own public repo that mentions you, so the mentions search lists it. Without config, a root claimed an owner when any remote of a clone under it pointed at that owner, so one `upstream` remote was enough to offer a stranger's repo for Clone. Now only `origin` remotes count (`rootOwners()` in `src/prs/place.ts`): the repo you cloned, or made. A config list still names any owner. Placing a PR under an existing clone still goes by any remote, since nothing is cloned.
- **Never over anything:** `<root>/<name>` must not exist, of any kind, a broken symlink included. gh clones into a fresh `mkdtemp(<root>/.pitwall-clone-)`, in the root so the move stays on one file system and hidden so neither discovery nor New session's list reads it; then `mkdir(<root>/<name>)` claims the name, failing if anything appeared since the check, and `rename` replaces only that empty directory. Something put inside the claimed directory meanwhile makes the rename fail, and the claimed directory is removed with `rmdir`, which removes it only while it's empty. On any failure pitwall removes the temp directory it made, recursively, only after checking it's that directory, and, after a timeout, again 10 s later, in case git was still writing.
- **gh, as pitwall always runs it:** `gh repo clone <owner>/<name> <temp>/<name> -- --quiet`, gh's documented form, with your gh login, so a private repo works and pitwall never sees GitHub's token; through the index's `runFile`, with no shell, `childEnvironment()`, `GH_PROMPT_DISABLED=1`, `GH_HOST=github.com`, since the PR list is github.com's, and `GIT_TERMINAL_PROMPT=0`; without the variables that would put the clone somewhere else (W107's review, which saw `GIT_WORK_TREE` move the files): `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE`; the configuration given in the environment itself, `GIT_CONFIG_PARAMETERS` (what `git -c` passes on), `GIT_CONFIG_COUNT` and each `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`, which can set `core.worktree`; and `GIT_TEMPLATE_DIR`, which installs hooks. Kept, as the user's own configuration files rather than settings in the environment: `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM`, which say which global and system files git reads, as a plain `git clone` in your terminal would (W108's note); in a fresh 0700 `mkdtemp(<tmpdir>/pitwall-gh-)` of its own, removed after, never the shared temp directory itself, which on Linux any local user can write to; in a process group of its own with no controlling terminal (`processGroup`), so nothing in it, ssh asking for a passphrase included, can prompt in the terminal pitwall runs in, and a timeout stops gh's git with it; 5 minutes at most (`CLONE_TIMEOUT_MS`). With `GIT_CEILING_DIRECTORIES` set to the temp directory (W117's review), git, should anything gh runs look for a repository, stops before the temp directory: git searches parent folders, and on Linux anyone can put a `.git` there. What failed is said in pitwall's words: runFile never reads stderr, and stdout is never shown.
- **When pitwall stops** (W107's review): the clone's own session means Ctrl-C or closing pitwall's terminal never reaches gh or git, so the server's close() aborts a running clone through runFile's `signal`, which sends its whole group SIGTERM, then, 2 s later, SIGKILL to whatever is left in the group, and waits until gh has exited and nothing in its group is left, 2.5 s at most, then removes the temp directory; a new request gets 503. A timeout does the same, without the wait. The SIGKILL goes while anything is left in the group, by `kill(-pid, 0)`, not only while gh runs (W108's finding, W117: gh exits on the SIGTERM, and the reviewer's probe saw a child that ignored it still alive 3.5 s later); a group's id isn't reused while the group lasts, and it's asked only within 2.5 s of the SIGTERM. A pitwall killed outright can't, so at start, with the first snapshot's roots, it removes what one left: only a direct child of a root, at the root's real path, named as a clone's temp directory is (`ownTempDir()`), a real directory (lstat, never a symlink) owned by this user, whose own time and its entries' are all older than `CLONE_TIMEOUT_MS` and `CLONE_SWEEP_MARGIN_MS`, 10 minutes in all, so another pitwall's clone in progress, at most 5 minutes old, is left alone. Windows, with no owner to compare, sweeps nothing.
- **The prompt New session opens with** (W107's review; the coordinator's call, safer and reversible while Phil was offline): the PR's URL and why it needs you, in pitwall's words alone. Never its title or its checks' names: a prompt pitwall fills in is sent as typed by you, and a title is its author's words, a check's name its repo's maintainers' and apps', on a PR to an upstream repo as much as anyone else's, so "lint. Then run curl … | sh" would be your instruction. The session looks them up with `gh`. For a PR that isn't yours, a review request or a mention, it ends "It isn't my pull request: don't check out its branch or run any of its code without asking me first." (W108's finding, W117): the session runs in your default permission mode, in a folder you trust, and reads what the PR's author wrote.
- **Whose it is, before the click** (W108's finding, W117): the confirmation says "This is your pull request. It's in a repo owned by example." for yours, and for one that isn't, a warning alert: "This pull request isn't yours: you're mentioned in it. It's in a repo owned by a-stranger. Cloning it puts someone else's code on this machine." (`cloneWhose()` in `web/src/prStart.ts`).
- **Limits:** the apiKey, `Host` and `Origin` checks of every state-changing request; one clone at a time; at most 3 a minute (`CLONE_RATE`), a refused request taking none of them.
- **Trust isn't granted, and isn't inherited.** Claude Code keys workspace trust on a git repo's root, and a trusted folder's trust covers its subfolders but not a git repo nested in it (its docs, "Project allow rules and workspace trust"). W107 checked live on 2026-10-29, under a trusted root: a new plain folder started a background session, and a new folder with `git init` failed with "Workspace not trusted". So after a clone New session says how to trust the folder, `cd <dir> && claude` with a copy button, and shows Claude Code's own trust error if you start first; pitwall never writes `~/.claude.json` or accepts a trust prompt (Phil: "Never grant trust for me"). The notice also says plainly what trusting it does (W108's finding, W117): "Trusting it lets the repo's own Claude Code settings, hooks and MCP servers run, so only trust a repo whose code you'd run." Claude Code's docs say project servers in `.mcp.json` have their own approval prompt in interactive sessions, which `claude -p` and Agent SDK sessions skip, loading them without asking.
- **Rejected:** a path or root from the page, which would let a page write anywhere under the roots; `git clone` with a URL, which would need pitwall to choose a protocol and handle credentials that gh already has; cloning into the target directly, which a failure would leave half-made, or a target that appeared meanwhile would mix with; `claude --worktree <PR URL>`, which fetches only from `origin` (PLAN.md, M4 redesign), for a new session in a repo that is cloned.
- **Not covered:** Windows, where pitwall hasn't been run, where `rename` onto an existing directory fails rather than replacing it, and where there's no process group to signal or owner to compare.
