## Who is this for

- Phil, who runs 15+ Claude Code sessions at once across Warp and Cursor.
- Agents working in this repo.

## Purpose

Stop losing track of Claude Code sessions: one place to see every session under a directory, what each one is waiting on, and act on it.

## Goals

- **See everything under a root.** `pitwall ~/work` lists every live Claude Code session whose working directory is the root or below it, wherever the session was started.
- **Group by directory.** Sessions sit under their git repo, with worktrees under the main repo, and fall back to the plain directory when it isn't a repo.
- **Act on a session.** Open it, read its conversation, reply, answer its prompts.
- **Spawn sessions.** Start a new session in any directory under the root.
- **See my open pull requests,** and the open ones that want my review or mention me, grouped by org, then repo, with review and CI state, next to the sessions working on them.
- **Talk to a supervisor.** One conversation that knows about every session: what's waiting, what's urgent and why. It can message or spawn sessions on my behalf. Going to a session directly stays possible.

## Non-goals, for now

- **Remote access.** Localhost only. Claude Code's Remote Control already gives phone and browser access to individual sessions.
- **Other agents** (Codex, Cursor's own agents). Keep one seam, a session-source adapter, so they can be added later, but don't build for them yet.
- **Multi-user or team use.**

## Measures of success

- I open pitwall instead of cycling through terminal tabs to find out what needs me. This is qualitative. The real test is whether I still lose track of a session after two weeks of use.
- A session that appears in `claude agents --json` under the root shows in pitwall within one poll: 5 s by default, plus the poll's own 0.2-1.3 s.
- The supervisor's triage matches a manual sweep like the one on 2026-10-16 (15 live sessions, 10 waiting on me) without me prompting each session.

## Context

### Why not an existing tool

Checked on 2026-10-16: Claude Code's agent view and Remote Control, Agent Deck, Muxara, Nimbalyst (formerly Crystal), Conductor, Claude Squad, crystl, opcode, Claude Code UI and kandev. Two gaps decided it:

- **Discovery.** The third-party managers only see sessions they launch, usually inside tmux. My sessions start in Warp and Cursor, and only Claude Code's own registry sees those.
- **Supervision.** Nothing ranks what every session needs from me. Agent view's per-row summaries and Agent Deck's "conductor" session come closest.

Agent view (`claude agents`) does much of the per-session work well. But it's a terminal UI, it only shows background sessions in the view, and it has no cross-session triage.

### Why not agent-control-room and kandev

kandev only manages agents it starts from its own cards. I start most sessions by hand, so it never saw most of my work. Pitwall adopts the sessions that already exist.

### Checked again: hub, Herdr and T3 Code (2026-11-26)

Phil asked how pitwall compares to [icons8/hub](https://github.com/icons8/hub), [Herdr](https://herdr.dev/) and [T3 Code](https://t3.codes/). The gap that decided pitwall still holds: none of them lists a session started outside it while that session runs.

- **hub** (Apache-2.0, public since 2026-11-19, labelled experimental): a coordinator session you talk to, which starts and runs Claude Code or Codex sessions on its own copy of Claude Code, one `claude -p` stream-json process each, in `bypassPermissions` mode. It has a Now tab, question cards with buttons, Telegram and a watchdog.
- **Herdr** (Apache-2.0, Rust): a terminal runtime for agents. It owns the terminals its agents run in, shows working, blocked or idle as each agent reports it, and has a phone app over SSH. It shows nothing above the terminal: no reasons, recaps, PRs or usage.
- **T3 Code** (MIT, v0.1.12): a desktop and web app for threads across about ten agent CLIs, with worktrees, diff review, commit and PR buttons, usage, and phone apps. At first run it imports conversations from the last 30 days once, as copies you continue in T3 Code; it doesn't watch sessions running elsewhere.
- **What Phil took from it** (2026-11-26): the suggestions in "Nice to have, later" (From the 2026-11-26 comparison), a watchdog in "M6 - Triage", and W218 (a lead session and its workers).

## Architecture

```
pitwall [root...]  ->  local server (127.0.0.1, per-run token)  ->  web UI
  |
  |- Session index   claude agents --json, grouped by git common dir, plus a transcript adapter
  |- Session view    transcript (read) + a PTY running `claude attach <id>` (background sessions)
  |- Spawner         claude --bg --name <name> "<prompt>" in a directory under a root
  |- Relay           claude -p stream-json, SendMessage only, behind a gate (D8), until M5
  '- Supervisor      a headless Claude Code session pitwall runs (M5, option B), with pitwall's MCP server
                     (list, read, spawn) and ListAgents/SendMessage to reach any local session
```

Observed while building M1 (Claude Code v2.1.301):

- **`claude agents --json` works from an untrusted directory.** The index runs it from the temp directory, so the result doesn't depend on where pitwall was started.
- **`startedAt` is epoch milliseconds,** not a string.
- **Transcripts write one content block per line,** and about two thirds of assistant messages are `tool_use` only. Text blocks with the same `message.id` belong together.
- **Transcripts also carry `origin.kind` and `last-prompt` entries.** Both are internal, but `last-prompt` is a cheaper source for the latest prompt if it's ever needed.
- **A snapshot is about 20 KB for 20 sessions,** and a poll takes 0.2 to 1.3 s.

## Security

A local web UI that can type into agents running in auto mode is a local remote-code-execution surface: anything that can reach it can run code as me.

- Bind to `127.0.0.1` only.
- Generate a random token per run, unless `PITWALL_TOKEN` sets a fixed one (W40), pass it to the browser through the launch file (D7), and require it on every API request and WebSocket. The page's own static files need none (M1's rule), only the `Host` check.
- **The token travels in three places** (W175, D7): the launch file, the URL fragment it redirects to, and, between two tabs of the same browser, a `BroadcastChannel`, encrypted.
  - A tab with no token asks the open tabs. It proves which server served it with a one-time link code the server put in the page when the browser navigated to it (`src/server/linkCodes.ts`), and the channel carries only that code's SHA-256 and, back, the token encrypted under the code (AES-GCM, `web/src/tokenLink.ts`). A tab answers only after the server confirms, over that tab's own signed-in WebSocket, that it issued the code and hasn't seen it used.
  - The code is given only to a navigation no page started (`Sec-Fetch-Dest: document`, `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Site: none`, no `Sec-Purpose`), never to a script's `fetch`, a frame (`frame-ancestors 'none'`) or a page's `window.open`, which arrives as `same-origin`. `Cross-Origin-Opener-Policy: same-origin` is defence in depth only: a stale page can send it too and keep its handle. The page blanks the tag once it has read the code. The server's `link-confirmed` carries a MAC under the token over the hash, the code and the origin, which the tab checks before it seals the token, so a process that took the port after pitwall stopped can't choose the code. At most 64 codes wait at once (the oldest is pushed out), each for 30 s, each redeemed once; a socket may confirm 10 in 10 s; a tab answers 10 requests in 10 s, and a hash only once. The token is never in a URL, `localStorage` or a cookie, and never on the channel in the clear.
  - F2, fixed (Phil chose the fix on 2026-11-16): a stale page from another account plus a local process of that account that forges Fetch Metadata could have obtained a code and so the token, so a code is now issued only when the TCP peer of the request's socket is a process owned by pitwall's own uid (`src/server/peerUid.ts`). A process running as your own user is out of scope: it can read `~/.pitwall/` and the launch file anyway. On macOS it asks `/usr/sbin/lsof` (no shell, 2 s timeout, at most 4 at once, about 60 ms) for the client end of the connection, ignoring pitwall's own pid, and every other process holding it must have pitwall's uid (lsof run by an ordinary user lists only that user's processes, so another account's process isn't found, which also means no code); on Linux it reads the uid column of `/proc/net/tcp` and `/proc/net/tcp6`. Any other platform, an error, a timeout, output it can't read or no match fails closed to today's sign-in notice. Residual: a small race between the check and the request (the process could exit and another take its port), and a process of another account that can inject into one of your processes is out of scope. The check matches the connection's exact addresses as well as its ports, in any state (W175's re-review, finding 1): a port-only match was beaten by a decoy, a socket of your own browser on `[::1]` with the same port numbers beside the other account's invisible `127.0.0.1` one; on Linux a half-closed socket of the other account still counts, and one ESTABLISHED row is needed. G2 (W175's re-review): a tab that an old page holds a window handle to (a pop-under it opened, with its own `Cross-Origin-Opener-Policy: same-origin`) and that you then reload or restore would get a code the old page reads, so a request with `Cache-Control: max-age=0` or `no-cache`, or a `Pragma` header, gets none; a link opened from a terminal sends neither (checked in Chrome 157, 2026-11-16). Residual, accepted: typing or pasting a pitwall URL into a window such an old page opened or holds still gives that window a code the old page can read (shown with a stand-in for the typed URL), since the server can't tell it from a link opened from outside; it needs an old page from another account on this port, the user's own navigation in its window, and a pitwall tab open with the token. Also out of scope: a connection forwarded through one of your own processes (`ssh -L`, a container proxy) passes the uid check, and a service worker an old page registered on the origin controls it with or without W175.
- Check `Host` and `Origin` on every request, to block DNS rebinding.
- No CORS.
- **`localStorage` holds no token, and no session content but session ids.** The token is in `sessionStorage` (M2), and so is each conversation's unsent draft (W44), the supervisor's included, with the text of any file you attach to it (W135; W164's I3); the browser keeps `sessionStorage` in its profile on disk (W48's F10).
  - `localStorage` holds UI state under `pitwall.*.v1` keys:
    - preferences (theme, sort, shortcuts, panel width, group-by, the tab a running background session opens on and whether the terminal takes the keyboard);
    - filesystem paths of roots and repos, in `pitwall.view.v1`, `pitwall.finished.v1`, `pitwall.root-tab.v1` and `pitwall.hidden.v1:<root>`;
    - starred sessions' ids and nothing else, in `pitwall.starred.v1` (W53);
    - until W154 replaced it with snoozes kept on the server, the sessions marked Not needed now, each one's id and a 64-bit hash of what it needed, in `pitwall.not-needed.v1` (W88), which the page now removes once as it loads;
    - and, until W106 replaced its list, the PR list's collapsed repo headings, each repo's 64-bit hash, never its name, in `pitwall.pr-repos.v1` (M4, W95), no longer read or written;
    - and whether the recap strip is collapsed, `true` or `false` alone, in `pitwall.recap-collapsed.v1` (M5, W111);
    - and, since W212, nothing of the spin-off proposals: the page only reads and empties the old `pitwall.spinOffs.v1` (each dismissed proposal's session id and a 64-bit hash of the block, never its text) to send it to the server once. `$PITWALL_HOME/spin-offs.json` holds ids, keys, times and a started session's name, never prompt text (W163; W164's I1; W212).
  - A repo that isn't cloned (W106) is never stored, as the selection or as hidden: its key is its GitHub name. M1's `pitwall.groups.v1` is no longer read or written. D14 has the detail.
- **One call off the machine: `gh api graphql` to github.com** (M4, W93).
  - The PR poller runs it with the user's own `gh` login, for their open pull requests, and since W101 the open ones that ask their review or mention them, three searches, one call per page of 25 (W105): at start, every 3 minutes, and on Refresh, but not within a minute of the last (W100).
  - GitHub's token stays inside gh, which pitwall never reads. gh runs in a fresh 0700 directory of pitwall's own, `mkdtemp(<tmpdir>/pitwall-gh-)`, one per fetch, removed after, never the shared temp directory itself (W108's finding, W117), as Clone and start runs it, with `GIT_CEILING_DIRECTORIES` stopping git's search for a repository at the temp directory (W117's review).
  - `--no-prs` turns it off, and then pitwall never runs gh. pitwall's own code makes no other call off the machine but Clone and start's (below) and `--connector-tools`' call to an HTTP connector you named (W184, below); the Claude Code commands and sessions it starts, the relay included, reach Anthropic as Claude Code always does.
- **Clone and start, after a click: `gh repo clone`** (W107, D25).
  - The page sends only a PR's repo to `CLONE_PATH`, with the apiKey, `Host` and `Origin` checks of every state-changing request; the server clones it only when its own current list has a PR in that repo placed 'not-cloned', into the root that place names, as GitHub spells the repo's name, refusing `.`, `..`, a leading dot and a target that exists.
  - Never into a root that is your home folder or holds it (W108's finding, W117), where a clone could make `~/bin`, on PATH under Ubuntu's default profile, or `~/Applications`, where editor detection looks. gh, with your login, clones into a fresh hidden `.pitwall-clone-*` folder in the root, through `runFile` with no shell, `childEnvironment()`, `GH_PROMPT_DISABLED=1`, `GH_HOST=github.com`, `GIT_TERMINAL_PROMPT=0`, and without the `GIT_*` variables that would put the clone elsewhere or configure it from the environment:
    - `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, each `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`, and `GIT_TEMPLATE_DIR`;
    - `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM` are kept, as the user's own config files.
  - From a 0700 working directory of pitwall's own, in a process group of its own with no terminal, for at most 5 minutes; `mkdir` then claims the target and `rename` moves the clone in, so nothing that appeared meanwhile is overwritten.
  - On a failure only that temp folder is removed; on the server's close() the clone's whole group gets SIGTERM, then SIGKILL 2 s later while anything in it is left, gh exited or not (W117), then its temp folder is removed; and at start pitwall sweeps such folders a killed pitwall left, only real directories of this user's directly in a root, more than 10 minutes old. One clone at a time, at most 3 a minute.
  - The confirmation says whose the PR is and who owns its repo, and warns, for one that isn't yours, that cloning it puts someone else's code on this machine; a root claims an owner from its clones' `origin` remotes alone (W117). pitwall never trusts the new folder: Claude Code's trust in a root doesn't cover a git repo inside it, so New session says to run `claude` there once, and that trusting it lets the repo's own Claude Code settings, hooks and MCP servers run.
- **Recaps send excerpts of transcripts to a model** (M5, W110, D26), with `claude -p` on Haiku 5.5 and whatever credentials and provider `claude` finds in pitwall's environment: the user's own Claude login by default, but an `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL` or Bedrock or Vertex variable where pitwall was started is passed on and used, as for the relay.
  - Per first recap, a session's first prompt (at most 3,000 characters), Claude Code's newest `away_summary`, its whole newest compaction summary (at most 12,000) and its latest turns (at most 24,000), as W123's Plan status sent before W172 folded it into the recap (W150); for an update, the first prompt (at most 1,500), the previous recap and the turns since (at most 8,000, and your own lines among the older ones since, up to 8,000 more, W152). Framed as data in random-id tags. Since W189 (recaps a cold reader can act on), every recap also sends `<session-info>`, the session's name and its repo, and `<your-messages>`, the user's later messages to it, at most 6,000 characters, inside the same frame.
  - Every recap also sends a `<pull-requests>` block inside that frame (W150): up to 5 of the session's strong PR links, matched with the open PR list pitwall already has, each with its repo, number, title (someone else's text: plain, one line, at most 300 characters, quoted with `<` and `>` escaped), draft, checks and review, or "no longer open: merged or closed" for one the session opened, only when the authored search worked, wasn't cut short and ran at least `PRS_POLL_INTERVAL_MS` after the session opened it. These include private repos' titles. No new `gh` call; none with `--no-prs`.
  - Once a running session's turn has ended and it's been idle 5 minutes since something new, or 15 for an update to its recap (W132); when its view opens with no recap, or a stale one once its turn has ended (W132); once per activity, by itself, for a finished or ended session that owns an open PR needing you (W128), so its transcript excerpts go without a click; and on Refresh; at most 2 at a time and 500 a local day (W132).
  - The call has no tools, loads none of the user's settings, saves no session, gets the relay's environment without the effort variables, with output capped at 8,192 tokens (4,096 until W189, when the thinking ran past it and the call was sent again) and prompt caching off, runs with no shell from `~/.pitwall/recap/` at 0700, where nothing is written, and is hidden from the list by its directory and its pid, and by its name only while the row is under 2 minutes old.
  - Its answer is read strictly (one surrounding code fence is stripped and a `waitingOn` that disagrees with the to-dos is derived from them, W126; the hidden-character rule stays whole), and a refusal says which check refused it, never with the model's text, and what it can change is what the page shows: the recap, the title, Needs you's 'recap' reason, which only adds, and a done background job's badge, "Waiting on …" in Done's place, with line 2 then naming the job's own PR from its job file (W170), which moves no row into or out of Needs you; at worst a hostile transcript chooses the title and that reason's line 2, up to 400 characters, so anything that reads recaps, the supervisor included, reads them as untrusted data. Since W189, a model's answer with every field and extra keys beside them has the extra keys left out unread and logged as a repair (`extra-keys`); a stored file with one is refused.
  - A message counts as the user's own through the relay only by an id the relay sent.
  - **Kept recaps** (W132): each session's newest recap of pitwall's own is kept across restarts in `~/.pitwall/recap-store/<session uuid>.json`, a 0600 file by rename in a 0700 folder of pitwall's own beside `recap/`, never in it, holding a version, the session id, when it was made, `throughAt` (the newest transcript entry it covers) and the recap's summary, to-dos, waitingOn and title as pitwall's strict reading kept them: no transcript excerpt, prompt, name, directory, token or cost.
  - Loaded when the engine starts, so a session whose transcript hasn't moved past `throughAt` isn't recapped again, a finished one for its PR included.
- **The flag log** (W153): each flag on a session in Needs you, and each undo, is a JSON line in `~/.pitwall/flags.jsonl`, 0600, opened without following a link, appended, and past 1 MiB rewritten by rename with its newest half.
  - A flag's line holds when, the session id, the Needs you reason and its text (the to-do, Claude Code's line, the question or the prompt, which is session content), the recap's times and source, where you clicked and the relay's outcome; never a name, directory, prompt or token.
  - Read back at start as untrusted: a regular file of this user's, not writable by group or others, at most 2 MiB, each line checked field by field. `scripts/flag-report.ts` reads it the same way.
- **The diagnostics log** (W165): each time a session enters or leaves Needs you, or its reason changes, and the PR poller's counts when they change, is a JSON line in `~/.pitwall/diagnostics.jsonl`, written like the flag log (0600, opened without following a link, owner checked, appended, past 2 MiB rewritten by rename with its newest half) and every line goes through the same field-by-field check before it's written as when it's read back, so a field that isn't one of the fixed shapes is never written and the file is read as untrusted. It holds IDs, fixed words and counts only: no transcript text, session name, PR title, recap, branch, path or token. Tests feed hostile text through a session's and a PR's text fields, and out-of-type values cast into every field the writer takes. A PR is named by `owner/repo#number`, which is an ID, but a private repo's name stays on this machine like the flag log's texts, and the report prints it, so check before pasting a report into a public issue. No off switch.
- **The lineage log** (W167): each link between a session and the one that carries on from it is a JSON line in `~/.pitwall/lineage.jsonl`, written like the flag log (0600, opened without following a link, owner checked, appended, past 1 MiB rewritten by rename with its newest half). A line holds when, the two session IDs, `how` (`clear` or `continue`), the background job's short ID, the working directory and the git branch (the branch only on an inferred line), and `inferred: true`; never a prompt, name, title, recap or other transcript text. No off switch, as for the diagnostics log: it holds IDs and paths only.
- **Clear and continue** (W168): `POST /api/sessions/:id/clear-and-continue` with `{ key }` types into a background job through this server's own `claude attach` PTY; `POST /api/sessions/:id/continued` with `{ shortId }` notes a link.   - **pitwall's MCP server** is at `/mcp` on the same server, outside `/api/*`: the `Host` check of every route, any request with an `Origin` refused, POST only, a bearer token made for each supervisor process, crypto random, compared in constant time and valid only while that process runs, written only into the 0600 MCP config in the supervisor's 0700 folder, so never in `ps`, and never the page's token or apiKey; JSON only, at most 64 KiB, one message at a time, at most 4 tool calls at once, approve's held calls apart.
  - Its read-only tools only read what pitwall already has, and frame every piece of text from a session, a recap or GitHub as untrusted data under `untrusted`, a PR's repo and URL included, with tag and zero-width characters removed (W120), within caps of 40,000 characters an answer; its prompt says never to follow it.
  - At worst a hostile transcript, or a hostile message, page or email a connector returns, steers what the supervisor tells you, what it proposes and what it puts in a connector's query, and you read every proposal in full before anything goes. Read-only bounds what a connector can change, not the arguments of a read.
    - **Accepted risk, Phil's option B** (W186's F1; Phil, 2026-11-12, in W191's item): reads run without a click, and the supervisor's panel shows each MCP call with its arguments, as JSON on one line, up to 200 characters (W192's G2). A read tool's arguments go to its service with no card, so a steered model could put a session's text in a query, and a tool that takes a URL, or fetches one, could send it to any address. Never choose such a tool: `--connector-tools` marks the common shapes, `[takes a URL]`, and never preselects them: an input named like an address (`url`, `uri`, `href`, `link`, `target`, `website`, `src` and others) or of an address's format, at any depth, in arrays and nested objects included, or a description that says it fetches or reads a URL, a web page or the web. A server can describe one so it isn't seen, and an OAuth connector listed through Claude Code shows no inputs, so the choice stays yours. The prompt says to put only the words a search needs in a query. `--no-supervisor` turns it all off, and pitwall then never runs it or a connector; `--no-connectors` turns the connectors off alone.
- **The supervisor's connectors** (W184, D28; spikes 016 and 017): each in `supervisor.connectors` in the config file, checked as the rest of it is (D24), with no value of a variable in it, only names (`src/supervisor/connectors.ts`, `connectorServer.ts`, the one piece W185's answer changes). Three routes, as spike 017 proposed:
  - **An HTTP server you sign in to through Claude Code's OAuth** (`url`, optionally `oauth` with a client id, a callback port and scopes, no headers): Claude Code keeps the sign-in, keyed by the server's name, type, URL and headers, and pitwall holds no secret. `pitwall --connector-tools <name>` prints the one-time sign-in, an interactive `claude --strict-mcp-config --mcp-config <file>` with the same entry. Until then it's `needs-auth`: the supervisor runs without it, logs so once, and leaves it out of every later start until pitwall restarts (W186's F5), since each start of one that isn't signed in writes Claude Code's OAuth discovery state to its credential store (spike 017, finding 3); no token. The printed sign-in loads none of your settings (`--setting-sources ''`), as the supervisor doesn't (W186's F8).
  - **An HTTP server with an `Authorization` header** that takes a variable, `${NAME}`: `https` only, or `http` to 127.0.0.1, `localhost` or `[::1]`; any other host, private addresses included, only over `https` (W184's choice: a hostname can resolve anywhere, so refusing private literals would add nothing); no user name or password in the URL. Only `Authorization` may carry a credential, and it must take it from a variable; any other header may hold literal, non-secret text only, never a variable, and none named like a credential (`Cookie`, `Proxy-Authorization`, or with key, token, secret, auth, session, password or credential in its name). W186 (F2) found that Claude Code, following a 307 from one host to another, drops `Authorization` but sends every other header, `X-Api-Key` included, on to the second host. An `https` redirect to `http` wasn't tested.
  - **A stdio server**, run only through `connectorLauncher.mjs`, which starts its command with exactly `PATH` (D23's) and the variables its `env` names, from its own environment, and no shell. Claude Code passes a stdio server its whole environment, its cross-session messaging socket and token included (spike 017, finding 6, and W184's own check), which would let a connector message a session without a card; the launcher drops them, and replaces itself with the command (`process.execve`), so no process is left whose starting environment, which `ps -E` shows, holds them (W186's F4). That is hygiene against a connector picking up what it was never given, not a boundary: any process of the same user can read the 0600 MCP config and Claude Code's environment anyway. A name a connector may never take: `PATH`, `PITWALL_*`, `ANTHROPIC_*`, `CLAUDE*`, `LD_*`, `DYLD_*` and the relay's code-loading variables.
  - **Values:** read from pitwall's environment at each start and written only into the supervisor's 0600 MCP config (below), never on a command line, into Claude Code's environment, a log line, the state file or the page. A connector whose variable is unset, or holds `${`, a line break or another control character but a tab, in a header or an environment alike (W186's F7), is left out of that start, and the log names the variable, never its value.
  - **No `${` reaches the MCP config:** Claude Code expands `${NAME}` in its entries from its own environment (spike 017, finding 5), so the config file's command, arguments and URL are refused with one, and an entry that would hold one once its values and pitwall's paths are in is left out of that start. A connector's name is lowercase letters, digits and `-`, never `pitwall`, and a tool's name letters, digits, `_` and `-`, so neither can expand or widen `--allowed-tools`.
  - **A connector's call** has a `timeout` of 60 seconds, not pitwall's 30 minutes.
  - **`pitwall --connector-tools <name>`** is the one path that starts a connector outside the supervisor, and only when you run it, saying first what it will run: a stdio command with the same variables in a fresh 0700 folder of its own, in a process group of its own stopped after, or a POST to the URL with its headers, following no redirect, so a header's secret goes to that host alone. For an OAuth connector it runs `claude -p` on Haiku with no tools, the strict flags and that connector alone in a 0600 file, stopped at its `system/init`. What it prints from the server, names and descriptions, is cut to plain lines with no control, format or invisible characters. It never writes the config file.
- **One change outside pitwall's home: node-pty's `spawn-helper`'s execute bits** (W169). On macOS, before each terminal attach, pitwall adds the execute bits to the `spawn-helper` in its own `node_modules`, which node-pty 1.1.0's prebuild ships without them and `npm ci` puts back so. It opens the file without following a link (`O_NOFOLLOW`, `O_NONBLOCK`), `fstat`s it and changes it through that descriptor only when it's a regular file of this user's whose owner can't run it, adding the three execute bits to its permission bits and nothing else, never a read bit, and dropping any setuid, setgid or sticky bit (W180's N6); anything else is left as it is, and the attach fails with node-pty's own error (W180's F1).
- **A child's PATH holds absolute directories only** (W98, D23), a POSIX protection.
  - An empty or relative entry (`.`, `a::b`, a trailing `:`, `bin`) makes a bare `claude`, `gh`, `git`, `ps` or `open` resolve in the child's working directory, and stop, remove and `claude agents` run in the temp directory, which on Linux every local user can write to, as gh did until W107 and W117.
  - So childEnvironment() keeps only PATH's absolute entries, in order, and sets PATH to `/usr/bin:/bin` when none is left, since an empty PATH also searches the working directory and a bash further down would pick its own default, which ends in `.`.
  - An entry that is `~` or starts with `~/` is the home directory, in its place, as bash reads `~` and `~/`, from the child's own `HOME` when that's absolute, else `os.homedir()`, so a literal `~/.dotnet/tools` keeps working (coordinator, 2026-10-29); `~user/...`, and a `~` entry whose home has a `:` in it, are dropped with the other relative entries.
  - Every process pitwall starts goes through it, the browser opener included, and editor detection searches the same PATH. On Windows, whose lookup searches the working directory first anyway and where pitwall hasn't been run, PATH passes through unchanged.
- **The config file holds no token, and can't weaken these rules** (W103, D24). `~/.pitwall/config.json`, or `--config`'s file, holds the roots and their GitHub owners, and the supervisor's connectors, whose commands run as you, so a writable config would run code (W184). A key named like a token anywhere in it is an error, since `PITWALL_TOKEN` comes from the environment only. On POSIX it must be the user's own and not writable by group or others, checked with fstat on the opened file. No setting binds beyond 127.0.0.1, turns off the token or skips the `Host` and `Origin` checks, and pitwall reads no per-repo config file.
- Don't write the token or session content anywhere outside `~/.claude`, except the launch file (D7), the tab's `sessionStorage` (D14), the files you attach to a new session (D20), the recaps kept in `~/.pitwall/recap-store/` (W132, above), which hold what a recap says of a session and no transcript excerpt, and the flag log, `~/.pitwall/flags.jsonl` (W153, above), which holds what Needs you showed for each flag. The diagnostics log, `~/.pitwall/diagnostics.jsonl` (W165, above), holds no session content: IDs, fixed words and counts.
  - The launch file is one HTML file at 0600 in `~/.pitwall/` at 0700, deleted once a page has used it, after 60 s, or on exit, whichever comes first (with a fixed token, only after 60 s or on exit). The relay gate's expectations (D8) hold a session name and a hash, never message text, in 0600 files in `~/.pitwall/relay-gate/` at 0700, each deleted when its request ends.
  - The supervisor's MCP config, which holds its process's bearer token and its connectors' entries with their variables' values (W184), is a 0600 file in `~/.pitwall/supervisor/` at 0700, removed when that process exits; its `state.json` there holds only its session id and its prompt's version (W113); its recipient gate's files in `~/.pitwall/supervisor/gate/` at 0700 hold the names of the sessions it may message and a ready marker, each 0600, removed when that process exits (W115).
  - Its approvals, their text included, are kept in memory only. Files attached to New session's first prompt (W79, W84) are kept in `~/.pitwall/attachments/<id>/` at 0700, each a 0600 file: an unused one for an hour, a used one for 7 days after its session started, and used ones past 500 MiB in all sooner, oldest first, since the session's transcript keeps their content.
  - A fixed token (W40) is the user's own, in their environment or the pitwall repo's `.env`; W48 found the CLI printing it at every start (F2); since W51 it's never printed, and `npm run dev` reads the `.env` only when it's yours and has no group or other permission bits.

### M6 - Triage

Urgency ranking with reasons (time-sensitive, waiting on a decision, housekeeping, closeable), using the session index, the supervisor and M4's PR and CI state.

- **The supervisor refines M1's `askedYou` heuristic:** starting from each idle session's recap (M5), it reads its latest turns and judges whether it really needs me, and how urgently. W69 (M3.1) moved Needs you onto `NeedsYou`'s reasons; this refines its `asked` reason, and can start from Claude Code's recaps (spike 007, finding 8).
- **Age is a signal.** In the W5a calibration, five flagged sessions had been quiet for 2 to 14 days, and at least one question was moot.
- **PRs and sessions together,** for example: "CI is failing on your PR, and the session that opened it is idle."
- **Blocked on someone else, not me** (Phil, 2026-10-28). Claude Code's own `blocked` state and needs line can mean waiting on another person or an event. My example: a background session that had posted a request-changes review and was waiting for the author's fix before it re-ran a check and tore down what it had started. I read it as done; W69 lists it in Needs you, since Claude Code says it's blocked. Triage tells waiting on someone else from waiting on me, and lists it under its own heading rather than Needs you. With M4's PR state, it notices the event, such as a new push to that PR, and tells me or the session. Until then, W88's Not needed now is the manual way.
- **The coordination model: split work, shared state, graded oversight, shared decisions first** (Phil, 2026-11-02; first written as "observer", then corrected and revised the same day; every source below was fetched and checked). "Observer" is an oversight axis (how much pitwall watches and may do), not a topology (who talks to whom). Sessions do the work and may message each other; pitwall watches through its index: state, recaps, to-dos and peer messages. It wakes the supervisor only on events that need judgement, such as a session waiting too long on a peer, two waiting on each other, or a batch finishing. **Batches:** given several pieces of work, it starts one session per piece, grouped as a batch in the panel, with one summary turn when the batch is done. W124 started this: the supervisor finds, drafts and summarises, Phil works in the sessions, and it never relays replies.
  - **Split the work so pieces don't overlap** (the core of batches). Claude Code's [agent teams](https://code.claude.com/docs/en/agent-teams): "Break the work so each teammate owns a different set of files." Anthropic's [C compiler post](https://www.anthropic.com/engineering/building-c-compiler): agents split easily when "each agent picks a different failing test", and on the Linux kernel kept hitting the same bug until a reference compiler let them work on different files. [CooperBench](https://arxiv.org/abs/2601.13295): two agents had "on average 30% lower success rates when working together" than doing both tasks alone. [Kim et al.](https://arxiv.org/abs/2512.08296): against a single agent, coordination helped by up to 80.8% on decomposable financial reasoning and hurt by up to 70.0% on sequential planning.
  - **Shared state, not relayed messages:** the repo, and a task list or ledger. The C compiler agents claimed tasks with lock files in `current_tasks/` and let git settle clashes; agent teams share a task list. Cursor's [Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents): equal-status agents coordinating through a locked shared file slowed to "the effective throughput of two or three"; planners handing tasks to workers "solved most of our coordination problems".
  - **An oversight layer with graded powers.** Reversible actions are automatic: pitwall's own watching and notices, holding, flagging. Destructive actions, and anything sent as Phil (messages, new sessions, resumes, stopping, merging), sit behind a card he approves, of the kinds LangChain's [ambient agents](https://www.langchain.com/blog/introducing-ambient-agents) names: notify, question and review. Cards are kept for what matters, since Anthropic's [auto mode post](https://www.anthropic.com/engineering/claude-code-auto-mode) found "users accept 93% of them anyway", and its [autonomy study](https://www.anthropic.com/research/measuring-agent-autonomy) that "effective oversight doesn't require approving every action but being in a position to intervene when it matters". Claude Code's [cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging) already says a message from another session "never counts as your consent".
  - **Settle shared decisions before a batch starts, and check the merged result against the goal** (Phil, 2026-11-02). Splitting the work stops pieces overlapping, but not pieces that are each fine yet disagree, and a watcher of state can't see that. Two parts, both cheap:
    - **Before a batch:** the interfaces, conventions and data shapes the pieces must agree on are settled once and go in each session's first prompt or a shared file in the repo. Only when the pieces share something; a batch of independent pieces skips it.
    - **At the end:** one goal check per batch, when the pieces come together: a model call reviews the combined result (each piece's PR or diff) against the batch's goal and reports to Phil. It's a report he reads, not a gate that merges or blocks anything, and it costs one turn per batch, never a continuous check.
    - **Evidence:** [CooperBench](https://arxiv.org/html/2601.13295) sorts the symptoms of coordination failures (GPT-5 categorised all failed cooperative runs; the paper doesn't state the base or the count): work overlap, 33.2%, and divergent architecture, 29.7%, where "Incompatible design decisions lead to semantic loss even under a clean merge." Splitting the work addresses the first, not the second. [MAST](https://arxiv.org/html/2503.13657v3) (Cemri et al., NeurIPS 2025, [poster](https://neurips.cc/virtual/2025/poster/121528)): 14 failure modes across 1,600+ annotated traces of multi-agent systems; its six inter-agent misalignment modes (2.2, 6.8, 7.4, 0.85, 1.9 and 13.2%) sum to about 32% of the failures, a total I added up, since the paper gives the per-mode shares and not their sum (and doesn't state their base).
  - **Never treat "idle for N minutes" as stuck.** A session at its usage limit looks the same. Gas Town's [gastownhall/gastown#4887](https://github.com/gastownhall/gastown/issues/4887) (Usage/session-limit block is indistinguishable from a hang in gt dog status), open and untriaged, reports that duration-based detection "literally destroys a healthy worker"; its [CHANGELOG](https://github.com/gastownhall/gastown/blob/main/CHANGELOG.md) removed the Deacon's kill authority in 0.2.3 and hung-session detection that "was killing healthy witnesses and refineries" in 0.11.0. A watcher flags and asks; it doesn't kill.
  - **A watchdog for loops, repeated errors and stalls** (Phil, 2026-11-26: "fold the watchdog into the triage idea"; from hub's `modules/watch/watch.py`). It adds a "may be stuck" reason: the same step repeated with no progress, the same error again and again, a turn with no new step for a long time, or a message the session never started a turn on. hub asks Haiku about a session's last 60 steps (at most 12,000 characters) when 100 new steps arrive, 3 minutes after the first new one, or after 10 silent minutes mid-turn. Its prompt starts from "Almost always — no", counts a long build or test run as normal, and alerts at most once per half hour per session. It reports and never fixes, as the rule above says.
  - **A quick "does it need me" check at the end of a turn** (from hub, for consideration): a Haiku call on the last 900 characters of the turn's final message answers `needs` and `ask` (one line, starting with a verb), and counts a wait on other sessions or processes as not needing the owner. It is narrower and sooner than a recap, which waits until the session has been idle 5 minutes, and could refine the `asked` reason above.
  - **The hub's cost is relaying content, not having a hub.** LangChain's [Benchmarking multi-agent architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures): the swarm "slightly outperforms" the supervisor, which "consistently uses more tokens" because of its "translation" of what sub-agents say. The supervisor already doesn't relay (W124). Multi-agent work costs more either way: Anthropic's [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) reports "about 15× more tokens than chats", and calls domains with "many dependencies between agents" a poor fit. Cognition's [Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working) (2026-04-22): it works when "writes stay single-threaded and the additional agents contribute intelligence rather than actions".
- **Spin-off proposals: a session proposes a new session, and you start it** (its first piece is W163, in M5.1; Phil, 2026-11-04; replaces the 2026-10-29 Suggested action, "A session asking the supervisor to spin off work"). For handing off separate work whose result shouldn't come back into the session's context, as a sub-agent's report would.
  - **The proposal:** the session ends its turn with a marked, fenced block: a folder, a name and the prompt. Sessions learn the convention from a `spin-off` skill shipped in pitwall's repo, installed once, so it works in every repo. The index finds the block in the transcript, as it finds `askedYou`, behind the transcript adapter, failing soft.
  - **The card:** in Needs you, labelled with the session that asked, with the whole prompt, the folder and the work profile's model. Start opens New session filled in, to edit before it runs; nothing starts without your click. The session's Conversation tab shows the block as a card with Start too, for as long as it's in the history (W209). The text is untrusted: the checks `spawn_session` runs (`src/server/supervisorActions.ts`), such as the folder under a root and no invisible characters, are reused, not rewritten. The new session records which session proposed it; the proposer never gets its result.
  - **Overlap first, without a model:** the card lists sessions, live or ended, in the same repo or folder whose names or recaps share words with the proposal, each with "Send to this one instead" (a message, or a resume for an ended one, with its size where the index has it) beside Start new. Duplicate work costs the weekly usage and can clash in one repo; a dormant session may already hold the context. Resuming re-reads that session's whole context, so a large one can cost more than a fresh session with a good prompt.
  - **"Ask the supervisor" on the card,** for judgement the word match can't make: the same work in other words, or which candidate has the context. You start that turn after reading the proposal, so D4 (the supervisor: read-only tools, acts only after your click) holds, and its suggestions come back as its usual spawn_session and resume_session cards. If the word match keeps missing, that's the evidence for the supervisor checking every proposal, decided from use.
  - **Not through the supervisor's inbox:** messages from other sessions stay refused (`crossSessionInbound: 'refuse'`). Routing requests through it would cost an Opus turn each and put a session's unread text in the context that sees every session. Nor `claude --bg` from the session's shell: in auto mode, or with Bash allowed, nothing asks you.
  - **Considering: start a proposal from a terminal, without pitwall's page** (Phil, 2026-11-23: "add D as considering"). A `pitwall spin-off <session id>` command you run in another terminal: it reads that session's newest `spin-off` block from the transcript itself, runs W163's checks (`checkSpawn()`), shows the folder, the name and the whole prompt, asks y/N, and on y starts the session with `claude --bg`. Not planned: W209's link (a link a terminal can open) covers a terminal while pitwall runs, and this would be a second way to start sessions, with its own security review. Built only if Phil finds he works in a terminal without pitwall's page open.
  - **Considering: a proposal that doesn't fill the terminal** (Phil, 2026-11-25: keep notes "for consideration in the plan, get the other planned work done, and then come back to this if still relevant"). Phil mostly reads sessions in a terminal, pitwall's Terminal tab included, where a `spin-off` block prints line for line.
