## Who is this for

- Phil, who runs 15+ Claude Code sessions at once across Warp and Cursor.
- Agents working in this repo.

## Purpose

Stop losing track of Claude Code sessions: one place to see every session under a directory, what each one is waiting on, and act on it.

## Goals

- **See everything under a root.** `pitwall ~/work` lists every live Claude Code session whose working directory is the root or below it, wherever the session was started.
- **Group by directory.** Sessions sit under their git repo, with worktrees under the main repo, and fall back to the plain directory when it isn't a repo.
- **Act on a session.** Open it, read its conversation, reply, answer its prompts.
- **Spawn sessions.** Start a new session in any directory under the root.
- **See my open pull requests,** and the open ones that want my review or mention me, grouped by org, then repo, with review and CI state, next to the sessions working on them.
- **Talk to a supervisor.** One conversation that knows about every session: what's waiting, what's urgent and why. It can message or spawn sessions on my behalf. Going to a session directly stays possible.

## Non-goals, for now

- **Remote access.** Localhost only. Claude Code's Remote Control already gives phone and browser access to individual sessions.
- **Other agents** (Codex, Cursor's own agents). Keep one seam, a session-source adapter, so they can be added later, but don't build for them yet.
- **Multi-user or team use.**

## Measures of success

- I open pitwall instead of cycling through terminal tabs to find out what needs me. This is qualitative. The real test is whether I still lose track of a session after two weeks of use.
- A session that appears in `claude agents --json` under the root shows in pitwall within one poll: 5 s by default, plus the poll's own 0.2-1.3 s.
- The supervisor's triage matches a manual sweep like the one on 2026-10-16 (15 live sessions, 10 waiting on me) without me prompting each session.

## Context

### Why not an existing tool

Checked on 2026-10-16: Claude Code's agent view and Remote Control, Agent Deck, Muxara, Nimbalyst (formerly Crystal), Conductor, Claude Squad, crystl, opcode, Claude Code UI and kandev. Two gaps decided it:

- **Discovery.** The third-party managers only see sessions they launch, usually inside tmux. My sessions start in Warp and Cursor, and only Claude Code's own registry sees those.
- **Supervision.** Nothing ranks what every session needs from me. Agent view's per-row summaries and Agent Deck's "conductor" session come closest.

Agent view (`claude agents`) does much of the per-session work well. But it's a terminal UI, it only shows background sessions in the view, and it has no cross-session triage.

### Why not agent-control-room and kandev

kandev only manages agents it starts from its own cards. I start most sessions by hand, so it never saw most of my work. Pitwall adopts the sessions that already exist.

## Architecture

```
pitwall [root...]  ->  local server (127.0.0.1, per-run token)  ->  web UI
  |
  |- Session index   claude agents --json, grouped by git common dir, plus a transcript adapter
  |- Session view    transcript (read) + a PTY running `claude attach <id>` (background sessions)
  |- Spawner         claude --bg --name <name> "<prompt>" in a directory under a root
  |- Relay           claude -p stream-json, SendMessage only, behind a gate (D8), until M5
  '- Supervisor      a headless Claude Code session pitwall runs (M5, option B), with pitwall's MCP server
                     (list, read, spawn) and ListAgents/SendMessage to reach any local session
```

### Interfaces pitwall relies on

| Drive a background session fully | `claude attach <id>` in a PTY | Documented command; embedding it in a PTY is ours |
| Message any local session, including interactive ones | The supervisor's `SendMessage` and `ListAgents` tools | Documented (cross-session messaging, v2.1.224+) |

| Clone a PR's repo that isn't cloned | `gh repo clone <owner>/<name> <dir> -- --quiet` | Documented (gh's manual). Run after a click only, into a temp folder in the root, then moved into place (W107, D25) |
| Conversation history | `~/.claude/projects/<dir>/<session-id>.jsonl` | **Internal.** The format changes between versions. Read-only, behind one adapter |

| A session's sub-agents | `~/.claude/projects/<dir>/<session-id>/subagents/agent-<id>.jsonl` and `.meta.json` | **Internal.** Read from W76, read-only, as part of the transcript adapter |
| A background job's "needs" line | `~/.claude/jobs/<id>/state.json` | **Internal**, and documented as not stable. Read from W69 (spike 007), behind one adapter, falling back to `claude agents`' state when it can't be read |
| Posting into a session's inbox socket directly | Unix socket under `/tmp/cc-socks*` | Only the auth line is documented. Don't depend on it |

Observed while building M1 (Claude Code v2.1.301):

- **`claude agents --json` works from an untrusted directory.** The index runs it from the temp directory, so the result doesn't depend on where pitwall was started.
- **`startedAt` is epoch milliseconds,** not a string.
- **Transcripts write one content block per line,** and about two thirds of assistant messages are `tool_use` only. Text blocks with the same `message.id` belong together.
- **Transcripts also carry `origin.kind` and `last-prompt` entries.** Both are internal, but `last-prompt` is a cheaper source for the latest prompt if it's ever needed.
- **A snapshot is about 20 KB for 20 sessions,** and a poll takes 0.2 to 1.3 s.

## Security

A local web UI that can type into agents running in auto mode is a local remote-code-execution surface: anything that can reach it can run code as me.

- Bind to `127.0.0.1` only.
- Generate a random token per run, unless `PITWALL_TOKEN` sets a fixed one (W40), pass it to the browser through the launch file (D7), and require it on every API request and WebSocket. The page's own static files need none (M1's rule), only the `Host` check.
- Check `Host` and `Origin` on every request, to block DNS rebinding.
- No CORS.
- **`localStorage` holds no token, and no session content but session ids.** The token is in `sessionStorage` (M2), and so is each conversation's unsent draft (W44); the browser keeps `sessionStorage` in its profile on disk (W48's F10).
  - `localStorage` holds UI state under `pitwall.*.v1` keys:
    - preferences (theme, sort, shortcuts, panel width, group-by, the tab a running background session opens on and whether the terminal takes the keyboard);
    - filesystem paths of roots and repos, in `pitwall.view.v1`, `pitwall.finished.v1`, `pitwall.root-tab.v1` and `pitwall.hidden.v1:<root>`;
    - starred sessions' ids and nothing else, in `pitwall.starred.v1` (W53);
    - the sessions marked Not needed now, each one's id and a 64-bit hash of what it needed, never the text, in `pitwall.not-needed.v1` (W88);
    - and, until W106 replaced its list, the PR list's collapsed repo headings, each repo's 64-bit hash, never its name, in `pitwall.pr-repos.v1` (M4, W95), no longer read or written;
    - and whether the recap strip is collapsed, `true` or `false` alone, in `pitwall.recap-collapsed.v1` (M5, W111).
  - A repo that isn't cloned (W106) is never stored, as the selection or as hidden: its key is its GitHub name. M1's `pitwall.groups.v1` is no longer read or written. D14 has the detail.
- **One call off the machine: `gh api graphql` to github.com** (M4, W93).
  - The PR poller runs it with the user's own `gh` login, for their open pull requests, and since W101 the open ones that ask their review or mention them, three searches, one call per page of 25 (W105): at start, every 3 minutes, and on Refresh, but not within a minute of the last (W100).
  - GitHub's token stays inside gh, which pitwall never reads. gh runs in a fresh 0700 directory of pitwall's own, `mkdtemp(<tmpdir>/pitwall-gh-)`, one per fetch, removed after, never the shared temp directory itself (W108's finding, W117), as Clone and start runs it, with `GIT_CEILING_DIRECTORIES` stopping git's search for a repository at the temp directory (W117's review).
  - `--no-prs` turns it off, and then pitwall never runs gh. pitwall's own code makes no other call off the machine but Clone and start's (below); the Claude Code commands and sessions it starts, the relay included, reach Anthropic as Claude Code always does.
- **Clone and start, after a click: `gh repo clone`** (W107, D25).
  - The page sends only a PR's repo to `CLONE_PATH`, with the apiKey, `Host` and `Origin` checks of every state-changing request; the server clones it only when its own current list has a PR in that repo placed 'not-cloned', into the root that place names, as GitHub spells the repo's name, refusing `.`, `..`, a leading dot and a target that exists.
  - Never into a root that is your home folder or holds it (W108's finding, W117), where a clone could make `~/bin`, on PATH under Ubuntu's default profile, or `~/Applications`, where editor detection looks. gh, with your login, clones into a fresh hidden `.pitwall-clone-*` folder in the root, through `runFile` with no shell, `childEnvironment()`, `GH_PROMPT_DISABLED=1`, `GH_HOST=github.com`, `GIT_TERMINAL_PROMPT=0`, and without the `GIT_*` variables that would put the clone elsewhere or configure it from the environment:
    - `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, each `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`, and `GIT_TEMPLATE_DIR`;
    - `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM` are kept, as the user's own config files.
  - From a 0700 working directory of pitwall's own, in a process group of its own with no terminal, for at most 5 minutes; `mkdir` then claims the target and `rename` moves the clone in, so nothing that appeared meanwhile is overwritten.
  - On a failure only that temp folder is removed; on the server's close() the clone's whole group gets SIGTERM, then SIGKILL 2 s later while anything in it is left, gh exited or not (W117), then its temp folder is removed; and at start pitwall sweeps such folders a killed pitwall left, only real directories of this user's directly in a root, more than 10 minutes old. One clone at a time, at most 3 a minute.
  - The confirmation says whose the PR is and who owns its repo, and warns, for one that isn't yours, that cloning it puts someone else's code on this machine; a root claims an owner from its clones' `origin` remotes alone (W117). pitwall never trusts the new folder: Claude Code's trust in a root doesn't cover a git repo inside it, so New session says to run `claude` there once, and that trusting it lets the repo's own Claude Code settings, hooks and MCP servers run.
- **Recaps send excerpts of transcripts to a model** (M5, W110, D26), with `claude -p` on Haiku 5.5 and whatever credentials and provider `claude` finds in pitwall's environment: the user's own Claude login by default, but an `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL` or Bedrock or Vertex variable where pitwall was started is passed on and used, as for the relay.
  - Per first recap, a session's first prompt (at most 3,000 characters), Claude Code's newest `away_summary`, its whole newest compaction summary (at most 12,000) and its latest turns (at most 24,000), as Plan status sends (W150); for an update, the first prompt (at most 1,500), the previous recap and the turns since. Framed as data in random-id tags.
  - Every recap and plan status also sends a `<pull-requests>` block inside that frame (W150): up to 5 of the session's strong PR links, matched with the open PR list pitwall already has, each with its repo, number, title (someone else's text: plain, one line, at most 300 characters, quoted with `<` and `>` escaped), draft, checks and review, or "no longer open: merged or closed" for one the session opened, only when the authored search worked, wasn't cut short and ran at least `PRS_POLL_INTERVAL_MS` after the session opened it. These include private repos' titles. No new `gh` call; none with `--no-prs`.
  - Once a running session's turn has ended and it's been idle 5 minutes since something new, or 15 for an update to its recap (W132); when its view opens with no recap, or a stale one once its turn has ended (W132); once per activity, by itself, for a finished or ended session that owns an open PR needing you (W128), so its transcript excerpts go without a click; and on Refresh; at most 2 at a time and 500 a local day (W132).
  - The call has no tools, loads none of the user's settings, saves no session, gets the relay's environment without the effort variables, with output capped at 4,096 tokens and prompt caching off, runs with no shell from `~/.pitwall/recap/` at 0700, where nothing is written, and is hidden from the list by its directory and its pid, and by its name only while the row is under 2 minutes old.
  - Its answer is read strictly (one surrounding code fence is stripped and a `waitingOn` that disagrees with the to-dos is derived from them, W126; the hidden-character rule stays whole), and a refusal says which check refused it, never with the model's text, and what it can change is what the page shows: the recap, the title and Needs you's 'recap' reason, which only adds; at worst a hostile transcript chooses the title and that reason's line 2, up to 400 characters, so anything that reads recaps, the supervisor included, reads them as untrusted data.
  - A message counts as the user's own through the relay only by an id the relay sent.
  - **Kept recaps** (W132): each session's newest recap of pitwall's own is kept across restarts in `~/.pitwall/recap-store/<session uuid>.json`, a 0600 file by rename in a 0700 folder of pitwall's own beside `recap/`, never in it, holding a version, the session id, when it was made, `throughAt` (the newest transcript entry it covers) and the recap's summary, to-dos, waitingOn and title as pitwall's strict reading kept them: no transcript excerpt, prompt, name, directory, token or cost.
  - Loaded when the engine starts, so a session whose transcript hasn't moved past `throughAt` isn't recapped again, a finished one for its PR included.
  - Read as untrusted, since anything running as the user can write it: the folder only when it's a real directory of the user's with no group or other access (`ensureLaunchDir()`), each file only when it's a regular file of the user's, not a link, not writable by group or others, at most 16 KiB, of at most 1,000, with exactly those fields, version 1, the session id its UUID name says, canonical times not in the future, and a recap that readRecapAnswer(), the check a model's answer gets, takes back unchanged; anything else is ignored and counted in the log, never with its text, and never shown.
  - So a planted file can say no more than a model's answer could, and Needs you's 'recap' reason from it only adds, as before. Removed when its session, listed earlier in the run, leaves a snapshot whose listing worked, and at load once both its times are older than 30 days (`RECAP_KEEP_MS`, the longest an ended session is listed, D17). Plan statuses stay in memory only.
  - The day's count is in `~/.pitwall/recap-budget.json` at 0600, the day, the calls and their cost and no session content, shared by a restart and a second pitwall on the same home. `npm run dev` passes `--no-recaps` unless `PITWALL_DEV_RECAPS=1`. `--no-recaps` turns it off, and then pitwall never runs a recap call and reads and writes no recap file. README's "What it reads" and "Security, in brief" say so.
- **The supervisor sends what it reads to a model, and acts only after your click** (M5, W112, W113, W115, D4).
  - One `claude -p` session on Opus 5.5, `pitwall-supervisor`, with whatever credentials and provider `claude` finds in pitwall's environment, as for recaps, started only when the page asks (Start, or your first message), never with pitwall and never again by itself after it stops.
  - It sends your messages, its system prompt and what its tools return: the listed sessions with their names, ids, repos, states, Needs you's reasons and text, recaps' summaries, owned PRs and last activity, as slim rows of at most 12,000 characters, filtered by repo, PR or words, and their directories and whole recaps only when it asks for detail (W124); a session's latest turns when it reads them, at most 40 entries or about 30,000 characters a call, each cut to 2,000; your open PRs with titles, failing checks' names, places and owners, those no session owns and not updated in 90 days only counted unless it asks for them (W125); a recap.
  - One built-in tool, `SendMessage` (`--tools SendMessage`), and `spawn_session` and `resume_session` (W127) on pitwall's MCP server, all three under `ask` rules, in `default` mode with `--permission-prompt-tool mcp__pitwall__approve`, so Claude Code asks pitwall before each call; the four read-only MCP tools allowed outright.
  - None of your settings, hooks, plugins, `CLAUDE.md` or MCP servers (`--setting-sources ""`, `--strict-mcp-config`), the relay's environment at the model's default effort, with MCP's timers at 30 minutes and no backgrounding of a long call, no shell, run in `~/.pitwall/supervisor/session/` at 0700, where nothing is written.
  - Your messages over stdin, never a command line; messages from other sessions refused; a permission prompt on the stream denied; stopped if a turn starts with a tool pitwall didn't give it, in another mode, or without its recipient gate; at most 30 agentic turns for one of your messages (`--max-turns`, W120).
  - Hidden from the list by its pid, folder, its name only in a supervisor's folder (W120), and session id; End session refuses it. **Approvals** (W115): `approve` shows each SendMessage, spawn_session and resume_session as a card on the snapshot, with its whole text, and holds the call until you Send, Edit or Don't send through `supervisorApprovalPath()`, with the apiKey, `Host` and `Origin` checks; anything else it's asked about is denied at once.
  - Checked before a card shows and again on your click:
    - a message only to exactly the name of one running, listed session, never an ended one, a shared name or pitwall's own, and, by a fresh unfiltered `claude agents --json --all`, as the relay checks, the only live session of that name, outside the roots included, with no `:` or `/` (W120), with only the fields pitwall knows and no idle notices;
    - a new session only in an existing directory under a root by real path, as New session requires, with New session's checks and limits, and never one of pitwall's own names;
    - a resume (W127, spike 011) only of a listed session by its id, resolved from the index's snapshot, after which only that session's own UUID, name and directory are used, never the input, as the Resume route uses its resolved summary: not pitwall's own, not running (a running one takes SendMessage, and a resume would start a copy), an ended interactive session or a background one that isn't running, not stale, its directory at or under a root by real path, and the message as a message's and never just a claude command's name, which the shared runner refuses too (W129);
    - its card says, as text, the session's folder, last activity and how many listed sessions share its name, and that it resumes with its own saved settings, permission mode included, with a warning when a stopped job's saved flags say bypassPermissions (W129, D4);
    - the Resume route's own code then runs it, with its fresh `claude agents` check, its directory check just before the run, its limits, and Claude Code's refusal of an untrusted workspace, as `claude --resume <uuid> --bg -- <message>`, so the message is on the command line, as spawn's first prompt is, and a copy Claude Code starts anyway is said on the hand-off and to the supervisor.
  - No text with a character that doesn't show as itself, a C0 or C1 control (so no terminal escape), a bidi, zero-width, tag or other format or default-ignorable character, in the message, prompt, recipient, name, directory or a resume's id (W120, D4); the card shows the exact string that goes, never filtered, with anything unusual left drawn as its code and a long text's line count.
  - A message through SendMessage ends with one fixed line of pitwall's after a blank line, never the model's (`SUPERVISOR_MESSAGE_FOOTER`, W138, D4): that it's from the supervisor, after your approval, and that a reply to it will be refused. Added after every check, to the allowed input only; plain ASCII; shown on the card apart from the text and the editor, so an edit can't remove it.
  - `spawn_session` runs pitwall's spawn, and `resume_session` pitwall's resume, only for a `tool_use_id` approve just allowed, with the input it allowed, once. Fails closed: denied after 29 minutes unanswered, when the call is cancelled, when the supervisor stops or pitwall closes, and for a malformed request; a deny-only `PreToolUse` gate on SendMessage checks the recipient again, before the card, against a list pitwall writes.
  - **pitwall's MCP server** is at `/mcp` on the same server, outside `/api/*`: the `Host` check of every route, any request with an `Origin` refused, POST only, a bearer token made for each supervisor process, crypto random, compared in constant time and valid only while that process runs, written only into the 0600 MCP config in the supervisor's 0700 folder, so never in `ps`, and never the page's token or apiKey; JSON only, at most 64 KiB, one message at a time, at most 4 tool calls at once, approve's held calls apart.
  - Its read-only tools only read what pitwall already has, and frame every piece of text from a session, a recap or GitHub as untrusted data under `untrusted`, a PR's repo and URL included, with tag and zero-width characters removed (W120), within caps of 40,000 characters an answer; its prompt says never to follow it.
  - At worst a hostile transcript steers what the supervisor tells you and what it proposes, which you read in full before anything goes. `--no-supervisor` turns it all off, and pitwall then never runs it.
- **A child's PATH holds absolute directories only** (W98, D23), a POSIX protection.
  - An empty or relative entry (`.`, `a::b`, a trailing `:`, `bin`) makes a bare `claude`, `gh`, `git`, `ps` or `open` resolve in the child's working directory, and stop, remove and `claude agents` run in the temp directory, which on Linux every local user can write to, as gh did until W107 and W117.
  - So childEnvironment() keeps only PATH's absolute entries, in order, and sets PATH to `/usr/bin:/bin` when none is left, since an empty PATH also searches the working directory and a bash further down would pick its own default, which ends in `.`.
  - An entry that is `~` or starts with `~/` is the home directory, in its place, as bash reads `~` and `~/`, from the child's own `HOME` when that's absolute, else `os.homedir()`, so a literal `~/.dotnet/tools` keeps working (coordinator, 2026-10-29); `~user/...`, and a `~` entry whose home has a `:` in it, are dropped with the other relative entries.
  - Every process pitwall starts goes through it, the browser opener included, and editor detection searches the same PATH. On Windows, whose lookup searches the working directory first anyway and where pitwall hasn't been run, PATH passes through unchanged.
- **The config file holds no token, and can't weaken these rules** (W103, D24). `~/.pitwall/config.json`, or `--config`'s file, holds the roots and their GitHub owners. A key named like a token anywhere in it is an error, since `PITWALL_TOKEN` comes from the environment only. On POSIX it must be the user's own and not writable by group or others, checked with fstat on the opened file. No setting binds beyond 127.0.0.1, turns off the token or skips the `Host` and `Origin` checks, and pitwall reads no per-repo config file.
- Don't write the token or session content anywhere outside `~/.claude`, except the launch file (D7), the tab's `sessionStorage` (D14), the files you attach to a new session (D20) and the recaps kept in `~/.pitwall/recap-store/` (W132, above), which hold what a recap says of a session and no transcript excerpt.
  - The launch file is one HTML file at 0600 in `~/.pitwall/` at 0700, deleted once a page has used it, after 60 s, or on exit, whichever comes first (with a fixed token, only after 60 s or on exit). The relay gate's expectations (D8) hold a session name and a hash, never message text, in 0600 files in `~/.pitwall/relay-gate/` at 0700, each deleted when its request ends.

### M6 - Triage

Urgency ranking with reasons (time-sensitive, waiting on a decision, housekeeping, closeable), using the session index, the supervisor and M4's PR and CI state.

- **The supervisor refines M1's `askedYou` heuristic:** starting from each idle session's recap (M5), it reads its latest turns and judges whether it really needs me, and how urgently. W69 (M3.1) moved Needs you onto `NeedsYou`'s reasons; this refines its `asked` reason, and can start from Claude Code's recaps (spike 007, finding 8).
- **Age is a signal.** In the W5a calibration, five flagged sessions had been quiet for 2 to 14 days, and at least one question was moot.
- **PRs and sessions together,** for example: "CI is failing on your PR, and the session that opened it is idle."
- **Blocked on someone else, not me** (Phil, 2026-10-28). Claude Code's own `blocked` state and needs line can mean waiting on another person or an event. My example: a background session that had posted a request-changes review and was waiting for the author's fix before it re-ran a check and tore down what it had started. I read it as done; W69 lists it in Needs you, since Claude Code says it's blocked. Triage tells waiting on someone else from waiting on me, and lists it under its own heading rather than Needs you. With M4's PR state, it notices the event, such as a new push to that PR, and tells me or the session. Until then, W88's Not needed now is the manual way.
- **The coordination model: split work, shared state, graded oversight, shared decisions first** (Phil, 2026-11-02; first written as "observer", then corrected and revised the same day; every source below was fetched and checked). "Observer" is an oversight axis (how much pitwall watches and may do), not a topology (who talks to whom). Sessions do the work and may message each other; pitwall watches through its index: state, recaps, to-dos and peer messages. It wakes the supervisor only on events that need judgement, such as a session waiting too long on a peer, two waiting on each other, or a batch finishing. **Batches:** given several pieces of work, it starts one session per piece, grouped as a batch in the panel, with one summary turn when the batch is done. W124 started this: the supervisor finds, drafts and summarises, Phil works in the sessions, and it never relays replies.
  - **Split the work so pieces don't overlap** (the core of batches). Claude Code's [agent teams](https://code.claude.com/docs/en/agent-teams): "Break the work so each teammate owns a different set of files." Anthropic's [C compiler post](https://www.anthropic.com/engineering/building-c-compiler): agents split easily when "each agent picks a different failing test", and on the Linux kernel kept hitting the same bug until a reference compiler let them work on different files. [CooperBench](https://arxiv.org/abs/2601.13295): two agents had "on average 30% lower success rates when working together" than doing both tasks alone. [Kim et al.](https://arxiv.org/abs/2512.08296): against a single agent, coordination helped by up to 80.8% on decomposable financial reasoning and hurt by up to 70.0% on sequential planning.
  - **Shared state, not relayed messages:** the repo, and a task list or ledger. The C compiler agents claimed tasks with lock files in `current_tasks/` and let git settle clashes; agent teams share a task list. Cursor's [Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents): equal-status agents coordinating through a locked shared file slowed to "the effective throughput of two or three"; planners handing tasks to workers "solved most of our coordination problems".
  - **An oversight layer with graded powers.** Reversible actions are automatic: pitwall's own watching and notices, holding, flagging. Destructive actions, and anything sent as Phil (messages, new sessions, resumes, stopping, merging), sit behind a card he approves, of the kinds LangChain's [ambient agents](https://www.langchain.com/blog/introducing-ambient-agents) names: notify, question and review. Cards are kept for what matters, since Anthropic's [auto mode post](https://www.anthropic.com/engineering/claude-code-auto-mode) found "users accept 93% of them anyway", and its [autonomy study](https://www.anthropic.com/research/measuring-agent-autonomy) that "effective oversight doesn't require approving every action but being in a position to intervene when it matters". Claude Code's [cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging) already says a message from another session "never counts as your consent".
  - **Settle shared decisions before a batch starts, and check the merged result against the goal** (Phil, 2026-11-02). Splitting the work stops pieces overlapping, but not pieces that are each fine yet disagree, and a watcher of state can't see that. Two parts, both cheap:
    - **Before a batch:** the interfaces, conventions and data shapes the pieces must agree on are settled once and go in each session's first prompt or a shared file in the repo. Only when the pieces share something; a batch of independent pieces skips it.
    - **At the end:** one goal check per batch, when the pieces come together: a model call reviews the combined result (each piece's PR or diff) against the batch's goal and reports to Phil. It's a report he reads, not a gate that merges or blocks anything, and it costs one turn per batch, never a continuous check.
    - **Evidence:** [CooperBench](https://arxiv.org/html/2601.13295) sorts the symptoms of coordination failures (GPT-5 categorised all failed cooperative runs; the paper doesn't state the base or the count): work overlap, 33.2%, and divergent architecture, 29.7%, where "Incompatible design decisions lead to semantic loss even under a clean merge." Splitting the work addresses the first, not the second. [MAST](https://arxiv.org/html/2503.13657v3) (Cemri et al., NeurIPS 2025, [poster](https://neurips.cc/virtual/2025/poster/121528)): 14 failure modes across 1,600+ annotated traces of multi-agent systems; its six inter-agent misalignment modes (2.2, 6.8, 7.4, 0.85, 1.9 and 13.2%) sum to about 32% of the failures, a total I added up, since the paper gives the per-mode shares and not their sum (and doesn't state their base).
  - **Never treat "idle for N minutes" as stuck.** A session at its usage limit looks the same. Gas Town's [gastownhall/gastown#4887](https://github.com/gastownhall/gastown/issues/4887) (Usage/session-limit block is indistinguishable from a hang in gt dog status), open and untriaged, reports that duration-based detection "literally destroys a healthy worker"; its [CHANGELOG](https://github.com/gastownhall/gastown/blob/main/CHANGELOG.md) removed the Deacon's kill authority in 0.2.3 and hung-session detection that "was killing healthy witnesses and refineries" in 0.11.0. A watcher flags and asks; it doesn't kill.
  - **The hub's cost is relaying content, not having a hub.** LangChain's [Benchmarking multi-agent architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures): the swarm "slightly outperforms" the supervisor, which "consistently uses more tokens" because of its "translation" of what sub-agents say. The supervisor already doesn't relay (W124). Multi-agent work costs more either way: Anthropic's [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) reports "about 15× more tokens than chats", and calls domains with "many dependencies between agents" a poor fit. Cognition's [Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working) (2026-04-22): it works when "writes stay single-threaded and the additional agents contribute intelligence rather than actions".
- **Spin-off proposals: a session proposes a new session, and you start it** (Phil, 2026-11-04; replaces the 2026-10-29 Suggested action, "A session asking the supervisor to spin off work"). For handing off separate work whose result shouldn't come back into the session's context, as a sub-agent's report would.
  - **The proposal:** the session ends its turn with a marked, fenced block: a folder, a name and the prompt. Sessions learn the convention from a `spin-off` skill shipped in pitwall's repo, installed once, so it works in every repo. The index finds the block in the transcript, as it finds `askedYou`, behind the transcript adapter, failing soft.
  - **The card:** in Needs you, labelled with the session that asked, with the whole prompt, the folder and the work profile's model. Start opens New session filled in, to edit before it runs; nothing starts without your click. The text is untrusted: the checks `spawn_session` runs (`src/server/supervisorActions.ts`), such as the folder under a root and no invisible characters, are reused, not rewritten. The new session records which session proposed it; the proposer never gets its result.
  - **Overlap first, without a model:** the card lists sessions, live or ended, in the same repo or folder whose names or recaps share words with the proposal, each with "Send to this one instead" (a message, or a resume for an ended one, with its size where the index has it) beside Start new. Duplicate work costs the weekly usage and can clash in one repo; a dormant session may already hold the context. Resuming re-reads that session's whole context, so a large one can cost more than a fresh session with a good prompt.
  - **"Ask the supervisor" on the card,** for judgement the word match can't make: the same work in other words, or which candidate has the context. You start that turn after reading the proposal, so D4 (the supervisor: read-only tools, acts only after your click) holds, and its suggestions come back as its usual spawn_session and resume_session cards. If the word match keeps missing, that's the evidence for the supervisor checking every proposal, decided from use.
  - **Not through the supervisor's inbox:** messages from other sessions stay refused (`crossSessionInbound: 'refuse'`). Routing requests through it would cost an Opus turn each and put a session's unread text in the context that sees every session. Nor `claude --bg` from the session's shell: in auto mode, or with Bash allowed, nothing asks you.
